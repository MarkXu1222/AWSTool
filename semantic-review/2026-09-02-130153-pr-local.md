# Single-instance lifecycle hardening for billing export jobs

This third pass rechecks only the billing-job closure and the `aws-service.ts` signal propagation added after the second review. The file-based lock is replaced by a loopback TCP listener, and cancellation now reaches payer/support STS, federation-token retrieval, and Puppeteer launch. The prior confirmed High and Medium findings are resolved; no new blocking concern was found in scope.

Watch for: **confirmed residual** — lock contention, startup/shutdown races, and launch-abort cleanup still lack automated regression coverage under the stated no-new-tests constraint.

**Verdict**: APPROVED

## High-level view

The runner uses an OS-owned listener on `127.0.0.1` as the cross-process lease. `exclusive: true` makes PM2 fork processes and cluster workers contend for one kernel bind, process death releases ownership without stale metadata, and duplicate instances exit instead of becoming concurrent JSON-database writers. This enforces the documented single-instance deployment model; it is not a horizontal cluster design.

Startup acquires the billing lock before scheduler and onboarding runners begin. Shutdown disables new billing submissions, aborts and drains the active run, then releases the lock while the HTTP server stops; the 30-second outer deadline exceeds the launch and browser/zip cleanup windows.

The job signal is composed with existing AWS deadlines for payer/support STS and the 20-second federation request, then passed into Puppeteer’s 20-second launch. Installed Puppeteer 25.1 registers abort before spawn and sends `SIGKILL` to Chrome’s detached process group; timeout/abort handling leaves its close path an additional cleanup window. After successful launch, bounded close still verifies exit and pauses the runner on unconfirmed cleanup failure.

The least-privilege boundary is preserved: member exports use strict `support-quota`, payer exports apply a `ReadOnlyAccess` session policy, and billing never falls back to an admin session.

## Loopback listener removes stale-lock ownership races

The prior lock protocols allowed contenders to reclaim filesystem state after observing incomplete or stale metadata. `acquireRunnerLock()` now delegates ownership to an exclusive kernel bind, so contenders cannot delete or reinterpret another process’s lease. This closes both the first-pass half-written-file race and the second-pass double-reclaimer race.

Forked PM2 processes contend independently, while cluster workers bypass Node’s shared-listener behavior for this lock because the bind is exclusive. A loser receives `EADDRINUSE`, closes its HTTP server, and exits. Multiple configured PM2 instances will therefore restart/exit extras rather than create duplicate runners, matching the explicit one-instance operational contract.

## Startup and shutdown preserve lock ownership

Any startup failure after binding releases the listener before propagating. The application awaits runner initialization before starting other background runners, while SIGTERM/SIGINT marks the runner unavailable before the first shutdown await, aborts active work, drains its promise, and releases the listener last. Queued jobs remain persisted for the next owner, and hard process death lets the OS release the socket automatically.

## Cancellation covers sign-in and browser startup

The external job signal is combined with local timeout controllers rather than replacing them. Payer and member billing paths pass it through `assumePayerForConsole()` or strict `assumeRoleStrict()`, and the federation `fetch()` receives the composed signal. Timer and listener cleanup occurs in `finally`; unrelated interactive admin/auto console paths remain outside this billing cancellation contract.

Puppeteer receives both the signal and a 20-second launch timeout. Its installed process layer starts Chrome detached, registers abort before spawning, and kills the process group on abort. A launch timeout starts Puppeteer’s close path while the local catch waits through the graceful/forced-close window; a resolved browser remains covered by `closeBrowserBounded()` and `BillingExportProcessCleanupError`.

## Residual lifecycle coverage — confirmed residual

The reported build, scoped diff check, and second-bind `EADDRINUSE` smoke test cover compilation and basic exclusivity. They do not simulate simultaneous PM2-style contenders through startup/exit, SIGTERM during STS/federation/launch, or timeout cleanup followed by immediate lock handoff. Future tests should assert one runner owner and no surviving Chrome/zip process before a successor acquires the port.
