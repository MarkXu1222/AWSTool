## Running Step Functions executions outlive the inventoried state machine

**High, confirmed:** `_scan_stepfunctions` inventories state machines and activities only (`scripts/cleanup.py:1111-1116`), while `_delete_StepFunctionsStateMachine` immediately requests state-machine deletion without listing or stopping running Standard Workflow executions (`scripts/cleanup.py:1727-1730`). AWS allows existing Standard executions to continue after state-machine deletion. Once the state machine disappears from `list_state_machines`, the execution is absent from this tool's inventory, so `command_verify` can compute `clean = true` from an empty residual set (`scripts/cleanup.py:2234-2236`) while execution work and charges continue.

Before deleting a Standard state machine, page through `list_executions` with `statusFilter="RUNNING"`, stop each execution, and model those executions in scan/plan/verify so failures remain visible. Express executions need an explicit documented disposition because they are not available through `ListExecutions`.

## CloudFront marker pagination stops unconditionally after page one

**High, confirmed:** after obtaining `NextMarker`, the Function and Key Group loops also test `FunctionList.IsTruncated` and `KeyGroupList.IsTruncated` (`scripts/cleanup.py:1255-1274`). In boto3 1.42.68, neither structure has an `IsTruncated` member; both expose `NextMarker` as the continuation signal. The missing field evaluates false, so both loops break after their first response even when `NextMarker` is present, and `verify` can omit residual functions or key groups.

Continue while `NextMarker` is non-empty, or add explicit pagination for these non-pageable operations. In the same correction, use the available paginator models instead of direct one-response calls for Internet Gateways and S3 buckets (`scripts/cleanup.py:900-902`, `1191-1198`).

## Validation scope
