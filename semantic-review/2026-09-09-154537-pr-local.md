# 移除 Cost Explorer，同时保留运营与账单导出流程

Web 生产版已删除 AWS SDK Cost Explorer 客户端及直接依赖、三条费用分析路由、账户详情费用查询和 Dashboard 定时费用刷新。Dashboard 改为运营计数，Billing 的 PDF job/历史/取消/ZIP/Excel 导入仍在，Cleanup 保留静态月费估算和删除确认。服务端类型检查与前端生产构建通过，但 Cleanup 新的区域来源会让“全部区域”扫描漏资源。**Watch for: confirmed — Cleanup 会漏掉 8 个硬编码区域之外的资源；confirmed — pnpm 锁文件同时升级了与 CE 无关的生产依赖。**

**Verdict**: NEEDS_CHANGES

## High-level view

Web 客户端调用、Express 路由、AWS service、scheduler、npm manifest/lock 之间的 CE 运行时链路已经断开；Billing export 的权限守卫和 job API 未被此次删减绕开。

Cleanup 失去 CE 返回的 billed regions 后，把固定的 8 个区域同时用作下拉选项和“全部区域”循环。直接扫描本身可用，但对在其它区域运行资源的账户会返回误导性的非完整结果。

npm 锁文件只做 CE 删除且校验通过，pnpm 锁文件则大范围重生成并选择了更新的 AWS SDK 与 Puppeteer。不同包管理器由此安装不同的生产依赖图。

历史审计展示与数据层清理没有同步完成：旧费用查询日志被重新归类为账单导出，Dashboard 成本缓存方法则在文档删除该字段后仍作为死代码保留。

## Cleanup “全部区域”实际只有 8 个区域 — High, confirmed

`Cleanup.tsx` 的 `REGIONS` 只有 8 项，却同时作为完整下拉来源和 `ALL_REGIONS` 的循环目标（`web/client/src/pages/Cleanup.tsx:15`, `:179`, `:282-283`）。改动前 CE 的 `byRegion` 可带出任意实际计费区域；现在 `ap-southeast-2`、`eu-west-2`、`ca-central-1` 和各 opt-in 区域都无法从页面选择，“全部区域（8 个）”扫描成功后仍可能遗漏最近资源。

区域来源应独立于 CE。现有 `api.getRegionStatus()`（`web/client/src/api.ts:532`）可提供平台区域状态；另一种方案是维护完整 AWS 区域目录，再按所选账户的 enabled 状态过滤。`ALL_REGIONS` 必须遍历该账户最终可用的区域集合，而不是 8 项 fallback。

## pnpm 锁文件重生成改变无关运行时版本 — Medium, confirmed

`package-lock.json` 仅删除 22 行 CE 条目，但 `pnpm-lock.yaml` 增加 881 行、删除 14 行。pnpm importer 把 Account、CloudFormation、Resource Explorer、SFN、SNS 客户端解析到 `3.1128.0`，Puppeteer 解析到 `25.10.0`（`web/pnpm-lock.yaml:16-49`, `:91`）；npm lock 对应版本则是 `3.1056.0`、`3.1092.0`、`3.1099.0` 和 Puppeteer `25.1.0`。使用 pnpm 的 CI/开发环境不会运行与生产 npm 部署相同的依赖图。

应明确 npm 是否为唯一 canonical lock：若是，回退 pnpm 的无关重生成；若两个锁都受支持，则把锁同步与版本升级拆开审查。`npm install --package-lock-only --dry-run` 和 `pnpm install --lockfile-only --frozen-lockfile --offline` 均通过，因此问题是依赖图分叉，不是锁文件语法损坏。

## 已删除路由改变了留存审计记录语义 — Low, confirmed

改动删除 `/api/aws/billing/by-account` 和 `/api/aws/billing/by-service/:accountId` 的专用展示规则，并把通用 `/billing/` fallback 改为 `账单导出`（`web/server/audit-presentation.ts:226-234`）。`audit_log` 中留存的历史 CE 查询因此会从“账单分析 / 查询账户账单（或服务账单）”变成“账单导出 / 查看数据”；`AuditLog.tsx` 同时删除了旧分类颜色。

保留仅用于历史展示的旧路径 matcher 和 `账单分析` 颜色即可，不需要恢复任何路由或 CE 调用。

## Dashboard 成本缓存数据层 API 已孤立 — Low, confirmed

`db.getDashboardCache()`、`db.setDashboardCache()` 的调用方已全部删除，但方法及 `dashboard_cache` 读写仍在 `web/server/db.ts:686-694`。README 与 project context 又把该字段从持久化数据说明中移除，造成代码表面与文档不一致，旧数据库中的缓存字段也不会被明确处理。

删除两个未使用 helper，并明确旧 `dashboard_cache` 是兼容性忽略还是一次性迁移。这里已经没有可达的 CE 调用，因此属于死代码与文档偏差，不是新增费用风险。
