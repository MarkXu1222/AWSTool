# Bounded AWS quota synchronization with one remaining null-write path

This revision closes the original quota-scheduler socket accumulation path by bounding regional fan-out, applying Abort deadlines, and destroying temporary clients after every settled operation. The scheduler now preserves a previously known current quota value when enrichment returns no value, and the worker pool waits for all sibling loops before propagating an unexpected failure. The same preservation was not applied to the three manual synchronization paths that call the changed enrichment function, so a timeout can still overwrite stored values there. No Critical or High concern remains. **Watch for:** **confirmed, Medium** — SSE, small-batch, and single-account sync still persist timeout-derived `null`; **confirmed, Low** — no automated regression test exercises cleanup, deadlines, worker draining, or value preservation.

**Verdict**: NEEDS_CHANGES

## High-level view

The incident path is closed: `listQuotaRequests` and `enrichCurrentValues` cap each account at six regional clients, the scheduler processes eight accounts per batch, and each client is destroyed from `finally`. Normal quota-history fan-out is therefore bounded at roughly 48 concurrent regional clients rather than one client per account-region pair surviving across batches.

Every changed STS, ordinary quota-list, single-quota, quota-increase, Bedrock, history, enrichment, and Account API operation now has a finite Abort boundary. `mapWithConcurrency` uses `Promise.allSettled` for its worker loops, so a rejection is rethrown only after all sibling loops and their client-cleanup blocks finish.

The scheduler fallback is null-safe and preserves a legitimate numeric zero, but three other persistence callers still write `_currentValue` directly. The timeout data-loss mode remains reachable outside the background scheduler.

Server TypeScript checking and diff whitespace validation pass. The project has no test command or focused coverage for these lifecycle and persistence behaviors.

## The 9,100-connection scheduler path now has deterministic ownership

`listQuotaRequests` creates at most six regional Service Quotas clients per account and destroys each one after success, SDK failure, or Abort at `web/server/aws-service.ts:894-914`. `enrichCurrentValues` applies the same six-worker bound and cleanup at `aws-service.ts:942-975`. Combined with the scheduler's eight-account batch at `web/server/scheduler.ts:123-129`, the quota-history phase peaks at roughly 48 regional clients; later batches cannot inherit completed clients from earlier batches.

The STS clients used by support-role and payer fallback paths are wrapped by `withAwsClient` and a 30-second Abort deadline at `aws-service.ts:121-218`. Ordinary pagination, single-quota reads, and quota-increase submissions use the same ownership/deadline pairing. The region scheduler shares one `AccountClient` across an account's regional calls, aborts the group after 30 seconds, waits for every send to settle, and destroys the client at `scheduler.ts:247-268`.

`mapWithConcurrency` now awaits all worker-loop settlements before selecting and rethrowing the first rejection at `aws-service.ts:92-115`. A rejected worker stops taking new items, but the current Bedrock, history, and enrichment workers absorb expected SDK failures internally; the helper cannot return or throw while sibling workers still own live clients. This resolves the previous fail-fast overlap concern.

## Scheduler value preservation is correct but not application-wide

At `web/server/scheduler.ts:132-160`, `r._currentValue ?? prev?.current_value ?? null` retains the previous snapshot only when enrichment is missing. Nullish coalescing preserves valid `0` values, and the same resolved value is used for change detection and persistence, so an enrichment timeout cannot erase a scheduler-cached value or generate a false quota-change notification.

**Confirmed, Medium:** the changed `enrichCurrentValues` still maps every failed or unfinished lookup to `null` at `web/server/aws-service.ts:949-968`. The SSE sync, small direct sync, and single-account sync call it and then persist `r._currentValue` without a previous-value fallback at `web/server/routes/aws.ts:1068-1084`, `1129-1145`, and `1160-1176`. A manual refresh during a slow region can therefore erase an existing `current_value` even though the background scheduler is protected. Apply the same fallback at every persistence boundary, or return explicit enrichment success metadata and refuse to overwrite known values on lookup failure.

## Deadline behavior is finite and cleanup follows settlement

The Account client uses one 30-second account-wide signal for all opt-in-region calls, quota history uses eight seconds per region, and Bedrock/enrichment use 15 seconds per region. Abort rejection is awaited before `destroy()`, and the all-settled worker pool prevents cleanup from racing a returned caller.

`assumeToAccount` can still take multiple 30-second windows while probing payer fallbacks, but each changed network request is finite; this is bounded latency rather than indefinite socket retention. Enrichment's 15-second budget covers all sequential quota lookups in a region, so later lookups may remain unknown under load and persistence must treat that state as partial rather than authoritative.

## Lifecycle guarantees lack executable regression coverage

**Confirmed, Low:** `web/package.json` defines no test script, and the diff adds no focused tests. Type checking cannot prove that `destroy()` runs exactly once on success/error/Abort, that concurrency never exceeds six, that worker rejection waits for sibling cleanup, or that all database writers preserve values after partial enrichment. Add mocked AWS-client tests plus persistence tests for scheduler and manual sync callers.
