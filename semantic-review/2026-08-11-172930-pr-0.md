# MAP Tag 全自动一键接入与持久化编排

这组变更把原来的手工前置资源创建、Resource Explorer 索引下发和 S3 配置保存串成了持久化后台任务，并在 React 弹窗中提供进度恢复与失败重试。正常路径的阶段边界和 S3 写后回读已经建立，但若出现并发全量保存、部分 StackSet 覆盖、服务停机或配置漂移，任务可能丢配置、卡在等待阶段或把未完成状态判为完成。`npm run build` 已通过；当前仓库没有覆盖这些恢复与并发场景的自动化测试脚本。

Watch for: **[confirmed]** 关闭弹窗后旧配置可覆盖后台 upsert；**[confirmed]** 部分 StackSet 覆盖只会等待而不会补建；**[confirmed]** 重启停机时间可能直接触发永久超时。

**Verdict**: NEEDS_CHANGES

## High-level view

S3 的 Promise 队列只保证单个 Node 进程内的写操作按顺序执行，并不提供对象版本比较。后台任务写入新组织后，页面仍能用旧的完整数组覆盖 `orgs.json`；弹窗关闭时轮询停止，完成回调不会刷新编辑器，使这条覆盖路径更容易发生。

StackSet 部署仍以“存在任意实例”或“区域出现过实例”为跳过条件，而新的等待阶段按 ACTIVE 成员账户与区域矩阵检查完整性。两套判断不对称：精确检查能发现缺口，但任务没有回到部署阶段修复缺口，只会等到超时。

等待阶段把持久化的 `phaseStartedAt` 与墙钟时间比较，并在读取 AWS 当前状态前判定超时。服务停机、PM2 重启或短暂网络故障都会消耗超时预算，即使 AWS 资源已经完成，恢复后的第一次执行仍可能直接失败。

DB 的损坏 JSON 会 fail-closed，但文件缺失仍被当作全新空库；写入使用同目录临时文件和 rename，却没有把临时文件及目录刷盘。任务恢复覆盖了正常进程重启，无法覆盖错误 DB 路径、文件意外缺失或主机断电的全部持久性风险。

路由沿用现有 MAP 写权限模型，但错误分类把存储故障、任务状态冲突和参数错误都压成 400。任务创建与审计又是两个独立 DB 写入，因此可能出现任务已接受、接口却返回失败的部分成功结果。

### High — S3 写队列仍允许陈旧全量配置删除新组织（confirmed）

`withOrgConfigWriteLock` 只在当前进程中串行执行函数，`putOrgsConfig` 仍会把调用方传来的整个数组直接写入 S3，而 `upsertOrgConfig` 只是队列中的另一个读改写操作（`web/server/tag-compliance.ts:97-100,158-200`）。如果后台 upsert 先完成，随后用户从较早加载的文本点击“保存到 S3”，后一个盲写会移除刚加入的组织；第二个 PM2 进程或任何外部写入者也完全绕过该锁。

前端放大了这条路径：轮询要求 `open === true`，关闭“后台继续”弹窗后不会再观察任务完成，`onCompleted` 也就不会调用 `loadConfig`；页面上的完整配置保存仍保持可用（`web/client/src/pages/TagCompliance.tsx:495-512,608,855-864,1019-1024`）。实际失败序列是后台写入新组织、弹窗关闭、编辑器保留旧数组、用户再保存旧数组。

修复应以 S3 ETag/VersionId 做 compare-and-swap：GET 返回版本，PUT/后台 upsert 使用 `If-Match`，冲突返回 409 并重新读取合并；后台 upsert 可在条件失败后有限重试。前端应把活动任务提升到页面级状态或在弹窗关闭后继续轻量轮询，完成时刷新配置；存在活动任务或配置版本过期时禁止盲全量保存。

### High — 非数组的 orgs.json 会被静默清空后重写（confirmed）

`getOrgsConfig` 对合法 JSON 但根节点不是数组的情况返回 `[]`（`web/server/tag-compliance.ts:144-152`）。新增的 `upsertOrgConfig` 随后把这个空数组当作真实配置，加上当前组织并写回，原对象内容因此被永久替换；这与 DB 新增的 fail-closed 目标相反。

应只对 `NoSuchKey` 返回空数组，对非数组根节点抛出配置损坏错误并禁止写入。写前还可保留 S3 VersionId，便于人工恢复。

### High — 部分 StackSet 覆盖能被发现，却不能被任务修复（confirmed）

AutoTaggerRole 只在实例总数为零时调用 `CreateStackInstances`（`web/server/tag-compliance.ts:818-839`）。Resource Explorer 两个 StackSet 只要目标区域存在任意账户实例，就把整区视作已部署（`web/server/tag-compliance.ts:989-1028`）。一次部分失败、历史遗漏账户或旧部署只覆盖部分 OU 时，这些函数都不会提交补建操作。

新的 `getOnboardingStackSetStatus` 会正确算出缺失的 ACTIVE 账户×区域键，但 `runWaitStackSets` 只轮询；超时和手工重试仍留在同一等待阶段（`web/server/tag-onboarding.ts:218-233`）。因此任务不是暂时等待，而是确定性地无法自愈。

部署阶段应基于同一个 expected-key 矩阵判断缺口，并针对根 OU/缺失区域重新提交幂等的 StackSet 实例操作。等待阶段发现长期缺口时应回到部署阶段，或直接执行一次受次数限制的修复，而不是只延长等待时间。

### High — ACTIVE 成员矩阵的状态归类会误失败，也可能误完成（confirmed）

校验把所有 StackSet 实例的 pending/failed 数量计入结果，包括已离开组织、非 ACTIVE 账户和不再要求的旧区域；这些范围外实例会让当前目标矩阵永远不 complete（`web/server/tag-compliance.ts:1313-1318,1344-1350`）。反向上，`actualKeys` 不区分实例状态，并把 `SKIPPED_SUSPENDED_ACCOUNT` 归为成功；一个当前已恢复 ACTIVE、但历史部署被跳过的成员可以满足 expected key，导致任务误完成。

应为每个 expected key 建立状态映射，仅对 ACTIVE 成员×requiredRegions 计算完成度，成功状态限于真正完成的 `CURRENT/SUCCEEDED`。范围外实例只作为诊断信息；`SKIPPED_SUSPENDED_ACCOUNT` 对 ACTIVE 目标必须视为缺失或失败。`DescribeStackSet` 结果还应校验 `SERVICE_MANAGED`、AutoDeployment 和根 OU 目标，否则当前矩阵通过后未来新成员仍不会自动覆盖。

### High — 重启恢复会在检查 AWS 前直接判永久超时（confirmed）

三个等待函数都先调用 `phaseTimedOut`，之后才查询 AWS（`web/server/tag-onboarding.ts:184-196,218-233,251-284`）。`recoverTagOnboardingJobs` 把 running 改回 queued，但保留旧 `phaseStartedAt`（`web/server/db.ts:272-287`）；如果服务停机超过 20/45/90 分钟，AWS 即使已完成，恢复任务也会在第一次查询前标记 failed。

应先读取当前 AWS/S3 状态，只在仍未满足条件时检查截止时间。若超时预算意在限制后台实际工作时间，应持久化累计运行时或在恢复时调整 deadline，而不是把进程停机时间算作 AWS 等待失败。

### High — DB 文件缺失仍会 fail-open 为全新空库（confirmed）

`readDB` 在 `DB_PATH` 不存在时直接返回 `emptyDB()`（`web/server/db.ts:136-140`）。生产环境中路径配置错误、挂载未就绪或文件被误删都会让服务以无用户、无审计、无 onboarding job 的空状态继续运行；随后的任意写入会在该路径建立新数据库，掩盖原数据不可用问题。

应区分显式首次初始化与生产数据文件缺失。生产启动时若预期 DB 已存在，应直接失败并告警；首次安装通过单独初始化命令或明确环境开关创建空库。

### Medium — rename 原子替换没有断电持久性保证（confirmed）

`writeDB` 写同目录临时文件后直接 rename，但没有对临时文件 `fsync`，也没有在 rename 后 `fsync` 父目录（`web/server/db.ts:154-165`）。这能避免普通进程崩溃留下半截 JSON，却不能保证主机断电后新文件内容和目录项都已落盘，旧文件又已经被替换。

应使用显式 fd 写入、`fsync(fd)`、关闭、rename，再 `fsync` 目录；写失败继续保留原文件并清理临时文件。若运行环境不支持目录 fsync，至少记录并明确降级策略。

### Medium — 已完成任务永久复用，不会验证漂移（confirmed）

同 payer、同 tagValue 的最新完成任务会被直接返回（`web/server/db.ts:196-200`），不会重新检查 S3 条目、角色、视图或 StackSet。配置被后续全量保存删除、StackSet 被修改或资源被人工清理后，再点一键接入只会展示旧的 completed，不会修复实际环境。

复用完成任务前应执行轻量 verify；验证失败时创建新 job，或把原任务重置到最早需要修复的阶段。完成记录可以保留作审计，但不能同时充当永久幂等键。

### Medium — 单个 AWS await 无截止时间，running 任务可在进程内永久卡住（likely）

阶段超时只会在函数获得执行权时检查；所有 AWS SDK 调用都直接 await，没有 AbortSignal 或请求级 deadline。若某次 SDK 请求不返回，job 已被写成 `running`，tick 会持续跳过它，`runningJobIds` 也只在 Promise settle 后释放（`web/server/tag-onboarding.ts:291-313,315-337`）。当前恢复逻辑只在进程重启时处理 running，无法在存活进程内回收失联执行。

应为每个 AWS 调用或整个 phase 设置 AbortController 截止时间，并把 running 状态改成带 lease/heartbeat；runner 应回收超过 lease 的任务并按幂等阶段重跑。

### Medium — 新建任务与审计非事务，错误状态码掩盖部分成功（confirmed）

提交路由先持久化并唤醒任务，再单独调用 `db.addAuditLog`；任一后续审计写失败都会落入统一 catch 并返回 400，即使任务已经存在且可能正在执行（`web/server/routes/aws.ts:51-73`）。retry 也把“不存在”“状态不允许”和 DB I/O 全部返回 400（`web/server/routes/aws.ts:93-100`），调用方无法区分输入错误、状态冲突和服务端持久化故障。

任务创建与审计应在一次 DB mutation/原子写中完成，或在部分成功响应中明确返回已接受的 job。参数校验用 400，不存在用 404，任务状态冲突用 409，存储/内部错误用 500 或 503；只有成功完成审计后再设置 `res.locals.audited`。

### Validation coverage

`npm run build` 通过了 Vite 生产构建和 server TypeScript 编译。仓库没有针对新增 runner 的测试脚本，因而没有自动验证崩溃点重放、超时边界、部分 StackSet 实例、S3 条件写冲突或关闭弹窗后的完成刷新；这些正是上述风险所在。
