# AWS SDK socket lifecycle and quota-sync preservation

This change closes the high-volume Service Quotas and scheduled Account client lifecycles, adds real abort signals, and limits quota-region fan-out with a draining worker pool. Current quota enrichment now retains the stored value when AWS returns no value or a request fails, and that behavior reaches the scheduler plus all three manual sync routes. The hot paths behind the production socket buildup are substantially improved, but the stated STS cleanup remains incomplete.

Watch for: **High, confirmed** — nine STS call paths still create clients without `destroy()`; **Medium, confirmed** — a new STS deadline can permanently poison the process-local support-role cache after a transient timeout; **Medium, confirmed** — no behavioral tests exercise the lifecycle, deadline, concurrency, or stale-value guarantees.

Severity summary: **Critical 0 · High 1 · Medium 2 · Low 0**

**Verdict**: NEEDS_CHANGES

## High-level view

Quota-region work now runs through a six-worker pool. Every Service Quotas client constructed in the changed paths is released, and the pool waits for all workers before propagating failure; the scheduled Account client similarly waits for its region requests, clears its timer, and is destroyed.

The abort controllers are passed into AWS SDK `send` calls and all introduced timers are cleared. **Medium, confirmed:** `tryAssumeSupportRole` still classifies every exception as permanent role unavailability, so its new timeout can disable the least-privilege path until process restart.

Enrichment filters stored records by `account_id` and then indexes by AWS request `Id`. Scheduler and all three manual sync routes persist the resulting `_currentValue`; scheduler adds another nullish fallback, while a failed history-region query returns no records and therefore cannot null existing rows.

**High, confirmed:** the new lifecycle policy is not applied to all STS clients in `aws-service.ts`. The dominant scheduled leak is addressed, but temp-admin, AssumeRoot, connection-probe, strict-role, and console credential paths retain the same leaking ownership pattern.

## STS cleanup stops at the quota assumption chain

**High, confirmed.** `withAwsClient` covers `tryAssumeSupportRole`, payer credential acquisition, and the two `assumeToAccount` fallback branches, but nine other STS constructions still call `send` without `destroy()`: `getTempAdminCredentials`, `assumeRoot`, the payer connection probe, `assumeRoleStrict`, `assumeAdminViaOAAR`, and `assumePayerForConsole` (`web/server/aws-service.ts` around lines 248, 262, 284, 331, 487, 1112, 1145, 1166, and 1196).

These paths are lower volume than scheduled quota collection but preserve the keep-alive ownership pattern behind the incident. Apply the helper to every temporary STS client, with an abort deadline where appropriate.

## Abort timeout is cached as permanent support-role absence

**Medium, confirmed.** `tryAssumeSupportRole` now gives STS a 30-second abort signal, while its broad catch adds the account to `supportRoleUnavailable` for every exception. A transient network stall, throttling delay, or abort therefore moves all later operations onto the payer/admin fallback chain for the rest of the process lifetime.

Only definitive role/trust failures should populate the cache. Abort, throttling, and transport errors should remain retryable or affect only the current operation.

## Lifecycle and stale-value guarantees lack regression coverage

**Medium, confirmed.** The scoped diff contains no tests for worker-pool draining, teardown on success/error/abort, timer cleanup, or current-value retention through scheduler and the three manual sync endpoints. Add focused tests with mocked AWS clients and fake timers that assert peak concurrency, settlement before rejection, one `destroy()` per client, abort propagation, and preservation of account-scoped prior values.
