# 持久化账单批量导出后台 job

这次重构把同步长请求改成了持久化 job：提交后进入全局单 job 队列，job 内有界并发抓取 PDF，随后异步打包、按 TTL 提供鉴权下载，并在重启时恢复 queued、终止 running/cancelling。抓取入口固定使用 `access='support'`，成员账户不会回退 OAAR/admin，payer 则由 `role/tool` 叠加 `ReadOnlyAccess` session policy；Express 路由顺序也没有被动态参数吞掉。主要风险集中在身份所有权仍按用户名判断、并发取消没有等待所有 worker 完全退出，以及队列没有准入上限。路径由服务端 UUID 与生成文件名构造，当前请求参数不能直接形成磁盘路径，但 TTL 下载存在检查与删除竞态。

Watch for: **[高][confirmed]** 删除并同名重建用户后会继承旧 job；**[高][confirmed]** 取消时首个 worker rejection 会让下一 job 在旧 Chrome worker 尚未完全退出前启动；**[高][confirmed]** 任意具备 billing 页面权限的用户可无限堆积 queued jobs。

**Verdict**: NEEDS_CHANGES

## High-level view

权限门禁在每个 job 端点实时读取数据库角色与 `allowed_pages`，单 job 查询、取消、下载也允许 admin 越权管理；问题是实时用户和 job owner 都用 username 关联，已经持久化但未使用的 `createdByUserId` 无法阻止同名账号接管旧产物。admin 的列表端点还被硬编码为仅列自己，与单 job 的 admin 边界不完全一致。

导出器的 support 会话约束是硬编码的，未发现从 job payload、路由参数或重试分支切回 `auto`/`admin` 的路径。取消信号能触达等待、活动 Chrome 和 zip，但 pool 用 fail-fast `Promise.all`，外层会在其余 worker 完成清理前删除目录并释放全局 job 锁。

队列在单 Node 进程内依靠同步设置 `activeJobId` 避免同一 tick 重复领取，重启时也会把 running/cancelling 明确标成 interrupted；不过领取没有持久化 lease/CAS，多进程部署会重复执行同一 queued job。队列也没有全局或每用户活动上限，active jobs 永不受 100 条终态裁剪限制。

DB 写盘采用临时文件、文件与目录 fsync、原子 rename，避免半截 JSON。代价是每完成一份 PDF 都同步重写并 fsync 整个 `db.json`，最大 200 份任务和最多 100 条历史结果会持续阻塞事件循环。

TTL sweep 会清理完成产物并把状态改为 expired，但下载端点在 `existsSync/statSync/createReadStream` 之间没有租约或已打开文件描述符，定时 sweep 可在流真正打开前删除文件。前端在 completed 后停止轮询，因此页面保持打开超过 TTL 后仍显示可下载，下载 410 也不会刷新状态。

审计轮询降噪规则只排除 GET list/status，submit/cancel/download 会显式落日志。新增 `describeApiCall` 路径映射不会作用于正常的 `BILLING_EXPORT_*` 显式日志，因为这些记录没有 method/path 且 `explicitActions` 未登记；cancel 又先改变状态再写审计，审计写失败时客户端收到 500，但取消实际上已经发生。

Nginx 的 10 分钟超时满足慢速 zip 传输需求，却被加在通用 `/` location，所有页面与 API 都放宽到 10 分钟，和文档所说的“zip 下载窗口”范围不一致。README 对 support、重启和 TTL 的描述基本对应实现，但“取消会关闭活动 Chrome/zip 并清理半成品”在 worker drain 修复前过度承诺。

## [高] Job owner 与实时用户都绑定可复用 username

**[confirmed]** `routes/aws.ts::requireBillingAccess` 通过 JWT 的 username 调 `db.getUser(username)`，不校验数据库用户 ID 是否等于 token 的 `userId`；`canAccessBillingJob` 同样只比较 `user.username === job.createdBy`（约 306-321 行）。`db.ts::BillingExportJob` 已保存 `createdByUserId`，但类型声明为 `string`，实际写入的是数值 `user.id`，后续 list/status/cancel/download 完全不使用它。用户管理允许删除账号后用同名重新创建，因此新账号可读取、取消和下载前任同名账号的 job；旧账号尚未过期的 JWT 在新账号也有 billing 权限时同样会重新通过门禁。

修复应把 `createdByUserId` 改为与用户 ID 一致的 `number`，`requireBillingAccess` 同时校验 `currentUser.id === tokenUser.userId`，owner 判断与列表过滤优先使用稳定 ID。只对历史上没有 `createdByUserId` 的记录保留 username fallback，并限制在迁移窗口。`routes/aws.ts` 的列表调用还应传入真实 admin 标志，或明确文档说明 admin 列表只看自己的任务。

## [高] Abort 会提前释放单 job 锁，旧 worker 仍可能运行

**[confirmed]** `billing-exporter.ts::runPool` 在约 503 行使用 `await Promise.all(workers)`。并发取消时，sleeping worker 往往先抛 `BillingExportCancelledError`，`Promise.all` 立即拒绝，而正在 `getConsoleSigninUrl`、Puppeteer 导航或 `browser.close()` 的其他 worker 尚未 settle；`exportBillingInvoices` 随即清理整个 workDir，`billing-export-jobs.ts::runJob` 随后把 `activeJobId` 清空并唤醒下一 job。这样“全局一次只跑一个 job”在取消窗口内不成立，旧 Chrome 还可能与下一 job 重叠，目录清理也可能和仍在写 PDF 的进程竞态。

应让 pool 在收到 abort 后停止领取新任务，但用 `Promise.allSettled(workers)` 排空所有已启动 worker，再向上抛取消。Chrome abort handler 不应只 `void browser.close()`；由 worker finally 统一 await close，并为卡死浏览器增加超时后 `browser.process()?.kill()` 的兜底。zip 的 SIGTERM 也应有短超时后的 SIGKILL，并等待 child close 后才允许 job 进入 terminal 状态。

## [高] Queued job 无准入上限，可形成持久化资源耗尽

**[confirmed]** `submitBillingExport` 只限制单 job 为 200 个任务，没有限制每用户或全局 queued/running/cancelling 数量。`db.ts::createBillingExportJob` 明确保留全部 active jobs，仅裁剪最近 100 条 terminal history。具备 billing 页面权限的用户可通过多标签页或直接调用 API 持续入队，使 DB 无界增长，并让单 job runner 排队执行数万次 Chrome 抓取。

提交前应原子检查并限制全局 active 数和每用户 active 数，超过时返回 429/409；同时对相同 owner + 规范化任务集提供 idempotency key 或短窗口去重。状态视图应返回总队列深度，便于管理员识别积压。

## [中] Job 领取仅在单进程内互斥

**[confirmed]** `billing-export-jobs.ts` 的 `activeJobId`、`tickInProgress` 和 `AbortController` 都是进程内变量，`tick` 对 queued job 做读取后再更新 running，没有持久化 claim token、lease 或文件锁。当前文档只描述一个 PM2 进程，因此单实例运行时同步赋值足以避免同进程重复领取；如果 PM2 切到 cluster、多实例并行启动或旧新进程重叠，两边都能执行同一 queued job并互相删除产物。

若设计只支持单实例，应在部署配置中固定 `instances: 1` 并在启动时取得进程锁，启动第二实例时 fail fast。若要支持 reload/cluster，应在持久层实现带 runner ID 和租约期限的原子 claim；JSON DB 不具备 CAS 时至少需要 OS 文件锁或迁移到支持事务的存储。

## [中] 每份 PDF 都同步 fsync 整库

**[confirmed]** `billing-export-jobs.ts::onProgress` 每得到一个结果就调用 `updateBillingExportJob`；`db.ts::writeDB` 每次都会序列化整个数据库、fsync 临时文件、rename，再 fsync 目录（约 209-230 行）。最大任务会做约 200 次全库同步写，历史 job 又保留 tasks/results，随着数据库增长会长时间阻塞 Express 事件循环，状态轮询、取消和其他业务请求都受影响。

进度持久化应按时间或批次合并，例如每 2-5 秒或每 5 个结果写一次，并在 phase/terminal 转换时强制 flush。内存仍可保留实时进度；重启最多损失一个小批次的展示结果，runner 按 interrupted 结束，不会错误续跑。

## [中] TTL sweep 与下载打开文件存在 TOCTOU

**[confirmed]** `getBillingExportDownload` 先 sweep、`existsSync` 后返回路径，路由再 `statSync` 并异步 `createReadStream`；独立的 60 秒 sweep 可在这些步骤之间把 completed job 目录删除并标记 expired。结果是已通过鉴权且刚返回可下载的请求可能在 headers 发出后 ENOENT。当前路径段来自数据库 UUID 与服务端生成文件名，请求参数只用于查 job，未发现直接路径穿越；但缺少 containment check 会让未来迁移或损坏记录扩大影响面。

应在决定可下载时同步打开只读 fd，再基于该 fd 创建流，并让 sweep 跳过有 active download lease 的 job；或者在开始下载时延长短租约，流 close 后释放。`resolve` 后还应断言路径位于 `resolve(OUTPUT_ROOT, job.id)` 下，并要求 `downloadFilename === basename(downloadFilename)`。

## [中] 审计失败会让响应与已提交状态不一致，展示映射也未命中

**[confirmed]** submit 对审计失败做 best-effort，但 cancel 在 `cancelBillingExport` 已写 DB 后直接调用 `db.addAuditLog`；该写入失败会进入 catch 并返回 500，即使 job 已经 cancelled/cancelling。download 则在开始 stream 前写审计，审计存储故障会阻止下载。`audit-presentation.ts::explicitActions` 没有 `BILLING_EXPORT_SUBMIT/CANCEL/DOWNLOAD`，而显式日志也没有 method/path，因此新增的路径 matcher只会在显式审计失败、通用 middleware 成功补记时生效，正常记录会退化成空路径的通用操作。

先确定统一策略：若审计是强制门禁，应在改变 job 状态前完成可事务化审计；若是 best-effort，cancel/download 应像 submit 一样捕获错误并返回真实业务结果。无论哪种策略，都应把三个 action 加入 `explicitActions`，并为日志补充 job ID、HTTP 结果与操作结果；下载日志若要表达成功，应在 stream `finish/close` 后记录，而不是在发送首字节前记录。

## [中] 前端不会感知已完成文件随后过期

**[confirmed]** `Billing.tsx` 只对 queued/running/cancelling 继续轮询，completed 后停止；下载按钮仅检查 `status === 'completed'`。页面保持打开超过 `expiresAt` 后仍展示“下载 ZIP”，`downloadBillingExport` 收到 410 只弹错误，不刷新 job。轮询 catch 对 403/404 等永久错误也固定每 4 秒重试，权限被撤销或历史记录被裁剪后会无限请求。

completed 状态应设置到 `expiresAt` 的定时刷新，或点击下载遇到 410 后重新获取 job 并更新为 expired。API 错误应保留 status code，让 polling 对 401/403/404/410 停止并清空或刷新 UI，只对网络错误和 5xx 退避重试。`loadRecentExportJob` 也应使用请求代次或 abort，避免首次恢复请求晚于新提交响应时覆盖新 job ID。
