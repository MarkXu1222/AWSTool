# Root password recovery without credential deletion

This change replaces destructive root-password deletion with AWS Organizations centralized root recovery. The service assumes the target account root under `IAMCreateRootUserPassword`, invokes `CreateLoginProfile` with an empty request, and preserves existing passwords by translating `EntityAlreadyExists` into an application conflict. The route retains the root-access authorization boundary, while the UI describes the non-destructive behavior. Watch for: none in the scoped diff; real AWS execution was intentionally excluded from validation.

**Verdict**: APPROVED

## High-level view

The recovery operation now uses a task-scoped root session and an empty `CreateLoginProfile` request. It neither deletes an existing root password nor supplies a replacement, and an already-present login profile is treated as a conflict rather than success.

The HTTP boundary remains protected by `requireRootAccess`. The service normalizes both AWS SDK `EntityAlreadyExists` names to `ROOT_PASSWORD_ALREADY_EXISTS`, and the route returns HTTP 409 only for that condition.

The confirmation and success messages no longer claim that a password is deleted. The version moves to 0.14.2, and the production build plus scoped diff checks pass without invoking AWS.

## Task-scoped recovery leaves existing passwords intact

`recoverRootPassword` calls `assumeRoot(accountId, ROOT_TASK_POLICY.createPassword)`, whose policy ARN is `arn:aws:iam::aws:policy/root-task/IAMCreateRootUserPassword`. Its only IAM mutation is `new CreateLoginProfileCommand({})`: there is no `UserName`, `Password`, `PasswordResetRequired`, delete command, or fallback that could overwrite or remove a root password. The IAM client is destroyed on both success and failure.

`DeleteLoginProfileCommand` remains imported only for the separate IAM-user cleanup path with an explicit username; root-password recovery cannot reach it.

## Existing root login profiles become HTTP 409 conflicts

Both `EntityAlreadyExistsException` and `EntityAlreadyExists` are converted into a stable service error code. The route maps only that code to HTTP 409, distinguishing the expected conflict from AWS, credential, and network failures; rejected operations do not write a success audit entry.

## Root-access authorization matches operator messaging

The endpoint remains declared with `requireRootAccess`, so this diff does not broaden the trust boundary. The UI continues to gate the action with `canRoot`, and its confirmation and success text describe mailbox-driven recovery without reading, generating, storing, or deleting the current root password.
