# Existing Resource Explorer local indexes as StackSet coverage

The change reclassifies a failed `ResourceExplorerLocalIndexes` StackInstance as covered only when its reason indicates `AlreadyExists` and live `GetIndex` data reports an `ACTIVE`, `LOCAL` index replicating to the configured aggregator region. Successful overrides are relabeled in `statusCounts`, while `web/client/src/version.ts` advances to `0.10.6`. The live-state predicate is strict, but credential-acquisition failures escape it and abort the full coverage inspection. Watch for: **confirmed** AssumeRole failures do not remain target failures; **confirmed** verification can fall back to an administrative role; **confirmed** candidates are checked serially with repeated STS calls; **confirmed** the branch has no targeted tests.

**Verdict**: NEEDS_CHANGES

## High-level view

The override is limited to the local-index StackSet, detailed status `FAILED`, an `AlreadyExists`-shaped reason, and all three required live index properties. Other terminal states and non-matching indexes remain failed.

The new verification boundary does not include credential acquisition. One member-account AssumeRole failure therefore rejects `getOnboardingStackSetStatus` instead of preserving that StackInstance's failure.

The platform-wide account helper can use a payer-mediated administrative fallback, and repeated regional candidates are verified one at a time with fresh role assumptions. This weakens least privilege and can make a polling status call scale poorly.

## Credential failure escapes the fail-closed override

Credential acquisition occurs before the `try` in `hasActiveExistingLocalIndex` (`web/server/tag-compliance.ts:1484`). A failed support-role attempt followed by failed fallbacks throws from `assumeToAccount`, and the inline await then terminates the complete three-StackSet inspection.

This is **confirmed** and violates the requirement that unverifiable cases remain failed. Create the client only after obtaining credentials inside the shared `try`, destroy an optional client in `finally`, and convert both AssumeRole and `GetIndex` errors to `false` so the original `FAILED` target and count remain unchanged.

## General account fallback exceeds the required privilege

The new call to `assumeToAccount` first attempts `support-quota` but can fall back through a payer to the member account's `OrganizationAccountAccessRole` (`web/server/tag-compliance.ts:1485`; helper at `web/server/aws-service.ts:176`). This **confirmed** path can run a read-only `resource-explorer-2:GetIndex` verification with administrative credentials and does not enforce a direct least-privilege assumption.

Use a strict exported support-role helper or a no-admin-fallback option that preserves ExternalId and timeout handling. Failure to acquire that role should leave the StackInstance failed.

## Polling latency grows across accounts and regions

The target loop awaits each verification inline (`web/server/tag-compliance.ts:1514`), and the support-role path obtains fresh credentials on every call. This is **confirmed**: five qualifying regional failures for one account cause five sequential STS calls and five sequential `GetIndex` calls on every poll.

Group candidates by account, assume once per account, and inspect regions with bounded concurrency. Apply the service's request timeout to `GetIndex`; `maxAttempts: 2` limits retries but not total wall-clock duration.

## Narrow AWS-state gate lacks regression coverage

No tag-compliance/onboarding test files are present. This **confirmed** gap leaves reason parsing, the exact `ACTIVE`/`LOCAL`/`ReplicatingTo` predicate, error isolation, and synthetic count accounting unprotected. Tests should cover each negative near-miss plus AssumeRole and `GetIndex` errors, and assert that an override preserves `instanceCount` and the total of `statusCounts`.
