# 成员账户清理器的身份保险丝、保留闭包与验收语义

脚本把凭证探测、扫描、计划、分轮删除和独立验收放进单账户流程；`scan`/`plan` 的调用树只使用 STS 与只读 AWS API，正常输入也不能绕过阶段、轮次和最终验收前的目标账号断言。管理员回退最终都会断言目标账号，但 payer 禁止名单仍只信任本地配置与缓存。当前不能用于“已清空”验收：扫描范围不是穷尽式，CloudFormation/IAM 保留关系没有形成闭包，默认 VPC 豁免过宽，并有确定的 CloudFront 响应解析错误。Watch for: **confirmed** 未扫描服务可让 `verify` 返回假 clean；**likely** 配置/缓存漂移可绕过静态 payer blocklist；**confirmed** 受保护 StackSet stack 会阻塞 IAM 清理且其受管资源仍可能被单独删除。

**Verdict**: NEEDS_CHANGES

## High-level view

直接 `admin-console` 与 payer→`OrganizationAccountAccessRole` 两条路径都会核对 STS Account，删除循环每轮也会重新核对。缺口是没有从 Organizations 实时确认目标不是管理账号且确属映射 payer；直接 admin 成功时不会验证 payer 会话。

扫描器采用显式服务白名单，而 `verify.clean` 把“已登记扫描器未发现资源”解释成“账号已清空”。未实现服务不会产生资源或 scan issue，形成系统性假阳性。

CloudFormation 没有建立 stack→物理资源所有权。普通 stack 会与其资源在同轮竞态删除，受保护 stack 的其他资源仍会被独立删除，而 stack 自身又会让 IAM/KMS 永久延后。

默认 VPC 的豁免按 `vpc_is_default` 传播到全部 subnet、route table 和 security group。自定义网络对象会被保留并计入允许残留。

<summary>Issues (10)</summary>

1. **[Critical][confirmed] 非穷尽扫描导致假 clean** — `verify` 只检查显式扫描器，未扫描服务会静默缺席；建立明确的覆盖契约，并让无法证明覆盖的验收 fail closed。
2. **[High][likely] payer blocklist 只信任本地状态** — stale/misbinding 的 `config.payers` 与 `accounts_cache._payer` 可让直接 admin 路径在未验证 Organizations 归属时进入管理账号；nuke 前应由映射 payer 实时确认 ManagementAccountId 与成员关系。
3. **[High][confirmed] CloudFormation stack 与受管资源竞态删除** — stack 触发删除后，同轮仍会直接删除扫描到的物理资源；建立所有权图，并在 stack 存在时只操作 stack，受保护 stack 的后代全部排除。
4. **[High][confirmed] 访问链保留闭包不完整并阻塞 IAM** — 受保护 stack、instance profile、附着 managed policy 没有统一 allowed-residual 语义，受保护 stack 还会让全部 IAM/KMS 永久 defer；将角色及依赖建成保留闭包并从依赖计数中排除。
5. **[High][confirmed] ServiceLinkedRole stack 检测缺口** — CloudFormation 只识别 `AWS::IAM::Role` 且只匹配配置角色名，包含 `AWS::IAM::ServiceLinkedRole`/`AWSServiceRoleFor*` 的 stack 仍可能被删除；扩展资源识别并复用统一的 service-linked 判定。
6. **[High][confirmed] 默认 VPC 豁免覆盖自定义网络对象** — 默认 VPC 内全部 subnet/route table/security group 都被允许残留，`verify` 可错误通过；仅豁免 default SG、main route table、`DefaultForAz` subnet 和基线 IGW。
7. **[Medium][confirmed] CloudFront KeyGroup 响应解析错误** — `ListKeyGroups.Items` 是 `{KeyGroup: ...}`，当前按扁平对象读取 `Id`；从 `item['KeyGroup']` 读取并隔离各子资源扫描错误。
8. **[Medium][confirmed] KMS 完成语义前后不一致** — nuke 把 `PendingDeletion` 排除并可报告 complete，verify 却把同一 key 当 residual，且未识别 `PendingReplicaDeletion`；统一 scheduled residual 契约并覆盖多区域 key 状态。
9. **[Medium][likely] 异步 no-progress 忽略状态变化** — fingerprint 只含资源 key，`ASYNC_TYPES` 不参与循环判定，重复 `triggered` 只在第一次算进展；按生命周期状态和 waiter/deadline 判断进展。
10. **[Medium][confirmed] 启用区域凭证失败仍允许部分删除** — nuke 忽略 `region_credentials_unavailable` 后继续删除，虽最终不会报告 complete，但会在清单不完整时执行不可逆操作；启用区域凭证失败应在删除前阻断。

## `verify` 把服务白名单误当作全账号证明

**[Critical][confirmed]** 区域扫描器在 `scripts/cleanup.py:834-867` 只覆盖 23 个入口，全局扫描器在 `scripts/cleanup.py:1186-1200` 只覆盖 S3、IAM、CloudFront、Route 53、Route 53 Domains 与 WAFv2。`command_verify` 在 `scripts/cleanup.py:2267-2273` 直接以“无 residual 且无 issue”生成 `clean=True`。仍有 Auto Scaling、EFS/FSx、ElastiCache、OpenSearch、Redshift、Kinesis/Firehose、AWS Backup recovery point、RDS Proxy/Global Cluster、MQ、App Runner、Lightsail、SageMaker/Glue 或 EC2 VPN/TGW/peering/Network ACL 的账号都可能通过验收。

验收需要版本化覆盖矩阵和独立兜底发现；无法权威枚举的服务/区域应输出 `coverage_unknown` 并 fail closed。Cost Explorer 和 Resource Groups Tagging API 只能辅助发现，不能单独证明零资源。

## 静态 payer 禁止名单缺少 Organizations 事实校验

**[High][likely]** `validate_target` 在 `scripts/cleanup.py:532-536` 只比较从 payer role ARN 解析出的 ID；`validate_member` 在 `scripts/cleanup.py:627-635` 只验证本地缓存和 `_payer` 名称。`assume_admin` 在 `scripts/cleanup.py:679-694` 先尝试直接 admin，成功后不调用 `assume_payer`。配置或缓存漂移时，目标账号断言只能证明“身份等于输入”，不能证明“输入不是管理账号”。

Destructive phase 前应由映射 payer 调用 Organizations，确认目标不等于 `ManagementAccountId` 且是该组织的 ACTIVE 成员；直接 admin 成功不能跳过。

## CloudFormation 所有权缺失会竞态删除或破坏受保护 stack

**[High][confirmed]** `_scan_cloudformation` 在 `scripts/cleanup.py:971-1010` 没有把 `list_stack_resources` 的物理 ID 回写到对应 `Resource`。`DELETE_ORDER` 在 `scripts/cleanup.py:1472-1547` 先删 stack，`delete_round` 随后继续处理同轮的 Lambda、ELB、RDS、EC2 等资源，可能制造 `DELETE_FAILED` 与 orphan。

`delete()` 在 `scripts/cleanup.py:1600-1602` 只跳过受保护 stack 对象，其受管但被其他扫描器发现的资源仍进入普通删除器。应建立 ownership map；普通 stack 存在时只触发 stack 删除并等待，受保护 stack 的全部后代从直接删除集合排除。

## 角色、策略、profile 与 stack 没有形成保留闭包

**[High][confirmed]** IAM 扫描在 `scripts/cleanup.py:1217-1247` 标记保留角色，但 `allowed_residual` 在 `scripts/cleanup.py:2212-2220` 不允许受保护 stack、对应 instance profile 或 customer-managed policy。策略删除器在 `scripts/cleanup.py:2188-2194` 发现保留角色附件后只返回 failure，verify 仍把策略视为 residual。

受保护 stack 也会在 `scripts/cleanup.py:1561-1571` 被计入 `dependency_resources_remain`，使所有 IAM/KMS 永久得到 `defer_until_service_resources_are_gone`。应构建角色、profile、policy、stack 与后代的保留闭包，并从 dependency gate 排除；`inspection_failed` 必须与“已证明含保留角色”分开，不能自动允许。

## Service-linked stack 不在递归保护规则中

**[High][confirmed]** stack 检查在 `scripts/cleanup.py:986-995` 只接受 `AWS::IAM::Role` 且 physical ID 位于配置角色集合。`AWS::IAM::ServiceLinkedRole` 和名为 `AWSServiceRoleFor*` 的普通 role 不会命中；stack 会先收到 `DeleteStack`，绕过 IAM 删除器的角色保护。

应同时识别两种 IAM 资源类型，并复用统一 `is_preserved_role` 判定；父子 stack 保护沿嵌套关系传播。

## 默认 VPC 标记把自定义对象一起豁免

**[High][confirmed]** `_scan_ec2` 在 `scripts/cleanup.py:934-940` 仅凭 `vpc_id` 属于默认 VPC 就设置 `vpc_is_default=True`。计划、删除器和 verify 在 `scripts/cleanup.py:1417-1420`、`1598-1600`、`2217-2219` 对 subnet、route table、security group、IGW 统一豁免，自定义对象不会删除也不会阻止 clean。

SG 应要求 `GroupName=default`，route table 要求 main association，subnet 要求 `DefaultForAz=True`，IGW 仅保留基线附件。默认 VPC 中未扫描的 Network ACL、route、peering 也必须纳入覆盖。

## CloudFront KeyGroup 会让整个服务扫描失败

**[Medium][confirmed]** `_scan_cloudfront` 在 `scripts/cleanup.py:1265-1275` 把 `ListKeyGroups` item 当作扁平对象。本地 botocore 1.42.68 model 确认 item 只有 `KeyGroup` 成员；存在 KeyGroup 时抛 `KeyError`，而 `_collect` 会丢弃该函数此前累积的 distribution、function 等结果并阻断 nuke。

应先取 `key_group = item['KeyGroup']`，并把各 CloudFront 子资源拆成独立错误边界。

## KMS scheduled 状态在 nuke 与 verify 中含义相反

**[Medium][confirmed]** `_delete_KMSKey` 在 `scripts/cleanup.py:2050-2058` 使用有效的 7 天窗口；nuke 在 `scripts/cleanup.py:2336-2338`、`2375-2383` 把 `PendingDeletion` 排除于 residual，因此可返回 complete。verify 没有相同例外；多区域主 key 的 `PendingReplicaDeletion` 也未识别。

如果 scheduled 算完成，verify 应单列并允许这些状态；否则 nuke 不能报告 complete。多区域 key 需要单独状态机。

## no-progress 只看资源 key

**[Medium][likely]** `Inventory.fingerprint` 在 `scripts/cleanup.py:251-254` 不含状态，`ASYNC_TYPES` 只用于 plan。循环在 `scripts/cleanup.py:2344-2354` 只把首次 `triggered` 或 category 为 `asynchronous/waiting` 的 action 视为进展；key 不变、API 重复返回 triggered 的异步资源可能三轮后提前停止。

应让生命周期状态变化计入进展，并为异步类型配置 waiter 与 deadline；幂等重触发不能替代完成条件。

## 启用区域凭证不可用不应降级为可删除

**[Medium][confirmed]** `issue_from_exception` 把 `UnrecognizedClientException` 归为 `region_credentials_unavailable`，nuke 在 `scripts/cleanup.py:2314-2318` 将其从 blocking issues 排除。区域已经由 `DescribeRegions` 过滤为 enabled，这类错误可能代表整个启用区域不可见；脚本仍会删除其他区域资源，只在最终 complete 上失败。

仅明确的 unsupported endpoint 可以忽略；启用区域的 credential failure 应在任何删除前阻断。
