# 持久化账单导出后台 job 与可取消下载流程

这次重构把同步导出改成持久化后台 job：提交后由单 job runner 串行调度，每个 job 内有限并发抓取，状态写入 JSON DB，前端轮询并在完成后鉴权下载。账单会话已固定传入 `support`，成员账户不会回退 admin；payer 管理账户由既有逻辑用 session policy 压成 readonly。重启时 queued job 会继续，running/cancelling job 会标记 interrupted 并清理产物。未发现高严重度问题，但取消收敛、owner 身份、队列背压、TTL/下载竞态和轮询可靠性仍有中严重度缺口。

Watch for: **[中][confirmed]** 同名用户重建后可继承旧 owner 权限；**[中][confirmed]** 取消时可能在旧 Chrome worker 全部退出前启动下一 job；**[中][confirmed]** zip/Chrome 终止没有硬超时；**[中][confirmed]** TTL 清理可与下载打开文件竞态；**[中][confirmed]** 轮询会在普通 HTTP 错误后静默停止。

**Verdict**: NEEDS_CHANGES

## High-level view

权限门禁实时读取数据库中的 billing 页面权限，单 job 的查看、取消和下载再执行 owner/admin 校验。**[中][confirmed]** owner 实际按 username 判断，`createdByUserId` 没有参与授权；admin 的列表调用又硬编码成仅列自己，造成授权模型和可管理性不对称。

runner 的进程内互斥能防止正常提交和 tick 同时启动两个 job。**[中][confirmed]** 取消路径的 `Promise.all` 会在首个 worker 拒绝后提前返回，`runJob` 可在其他 Chrome worker 仍关闭时释放全局槽位；zip 和浏览器关闭也没有强制终止上限。

重启恢复会把中断任务标为 interrupted，并保留 queued job。**[中][confirmed]** 队列没有全局或每用户容量限制，所有 active job 又不参与历史裁剪，因此具备 billing 权限的用户可以制造无界 backlog 和 DB 增长。

**[中][confirmed]** DB 每次创建 job 都会把终态历史裁到 100 条，尚未到期的 completed job 可能提前失去元数据。下载检查和定时清理之间也没有租约或原子文件句柄，临界时刻可在发送 ZIP 响应头后丢失文件。

下载文件名有 basename 和字符白名单。**[中][confirmed]** job 目录仍直接由持久化 `job.id` 拼接后交给递归删除，非法或穿越值会把删除范围带出输出根目录。

**[中][confirmed]** 前端每两秒轮询一次，但通用 request helper 不会因 429/5xx JSON 响应抛错，瞬时错误会让 UI 静默冻结。每个标签页每分钟约产生 30 次请求，也容易撞上全局每 IP 100 RPM 限制。

1. **[中][confirmed] Owner 使用可复用 username** — 删除用户后重建同名账号会继承旧 job/ZIP 权限；统一 `createdByUserId` 类型并以稳定 user ID 授权，仅对无 ID 的历史数据受控回退。
2. **[中][confirmed] Admin 列表权限不对称** — admin 可按 UUID 操作他人 job，但列表硬编码只返回自己；传入真实 admin 标志并展示 owner，或明确删除该隐含管理能力。
3. **[中][confirmed] 取消提前释放全局槽位** — `Promise.all` 首个拒绝后即返回，旧 Chrome worker 未 drain 完下一 job 就能启动；改为停止领任务后等待所有 worker settled。
4. **[中][confirmed] 外部进程终止无上限** — zip 只收 SIGTERM，Chrome 只走异步 close，卡住会永久占用队列；增加 grace timeout、SIGKILL/进程树升级和 exit 等待。
5. **[中][confirmed] 队列无准入与公平性限制** — 单用户可创建无界 active backlog 和 DB 记录；在持久化入队时实施每 owner/全局容量、幂等或去重及公平调度。
6. **[中][confirmed] 历史裁剪破坏 TTL** — 100 条终态上限会删掉仍未过期 completed job 的元数据和产物；未过期 completed 必须保留到 sweeper 完成到期转换。
7. **[中][confirmed] 下载与 TTL 清理存在 TOCTOU** — sweeper 可在异步打开文件前删除路径，导致 ZIP 头配 JSON 错误或断流；先打开 fd/获取租约，再用 `pipeline` 流式响应并在结束后释放。
8. **[中][confirmed] 递归删除缺少根目录约束** — 持久化 `job.id` 未验证就进入 `rmSync(recursive)`；严格校验 UUID，并以 canonical safe-join 保证所有路径都位于 output root。
9. **[中][confirmed] 轮询错误处理与限速冲突** — 429/5xx JSON 会让轮询静默停止，2 秒间隔又快速消耗 100 RPM；暴露 HTTP status，按错误类型停止或退避，并在后台标签页降频。
10. **[中][confirmed] 关键状态机无测试** — owner/admin、取消 drain、kill、重启、TTL 与下载竞态没有自动化覆盖；引入 fake exporter/clock/process adapter 后补集成测试。

### Owner 身份使用可复用 username，admin 又无法列出他人 job

**[中][confirmed]** `web/server/routes/aws.ts::canAccessBillingJob` 和 `web/server/db.ts::listBillingExportJobsForUser` 都用 `createdBy === username` 判断 owner。`createBillingExportJob` 已保存 `createdByUserId`，但它未用于授权，类型还声明为 `string`，实际由路由传入数字 `user.id`。`web/server/auth.ts` 允许删除用户后重新创建同名用户，因此新账号会获得旧账号的 job 状态、失败明细和 ZIP 下载权限。

修复应把 owner 主键统一成稳定字符串或数字，并在 `canAccessBillingJob`、列表过滤、取消和下载中优先比较 `currentUser.id` 与 `createdByUserId`；只有缺少该字段的历史记录才能受控回退 username。迁移后补一个“删除 Alice、重建 Alice、不能访问旧 job”的授权测试。

**[中][confirmed]** `GET /billing/export-jobs` 调用 `getBillingExportJobsForUser(user.username, false, limit)`，硬编码跳过 helper 已提供的 admin 分支。admin 可以通过已知 UUID 查看/取消/下载他人 job，却无法列出这些 job，也无法发现和处理堵塞全局队列的任务。若 owner/admin 是统一契约，应传入 `user.role === 'admin'`，在响应中保留 owner 字段，并在前端展示任务归属；若产品只允许 admin 按已知 ID 操作，则删除误导性的 `isAdmin` 参数并记录限制。

### 取消后全局 job 槽位先于 Chrome workers 释放

**[中][confirmed]** `web/server/billing-exporter.ts::runPool` 用 `Promise.all(workers)`。AbortSignal 会让多个 worker 同时拒绝，但 `Promise.all` 在第一个拒绝时立即结束；`exportBillingInvoices` 和 `web/server/billing-export-jobs.ts::runJob` 随即清理目录、把 job 标成 cancelled、清空 `activeJobId` 并唤醒 runner。其余 worker 的 `captureOne` 仍可能在等待 `page.close()`/`browser.close()`，所以取消时低内存服务器可能同时承载两批 Chrome。

修复应让 pool 在收到取消后停止领新任务，但等待所有已启动 worker `Promise.allSettled` 完成清理，再向上抛 `BillingExportCancelledError`。只有 drain 完成后 `runJob` 才能写 terminal 状态并释放 `activeJobId`。

### Chrome 与 zip 的取消没有硬终止边界

**[中][confirmed]** `web/server/billing-exporter.ts::createZip` 在 abort 时只发送一次 SIGTERM，然后无限等待 `close`。子进程忽略信号或卡在不可中断 I/O 时，job 会永久停在 cancelling，`activeJobId` 永不释放。`captureOne` 只调用 Puppeteer 的异步 `page.close()`/`browser.close()`，没有截止时间和 `browser.process()` 的进程级升级路径。

修复应建立统一的 bounded shutdown：先请求优雅关闭，经过短 grace period 后对仍存活的进程发 SIGKILL，并等待 exit/close；Chrome 记录 `browser.process()`，关闭超时后杀进程树。正常退出时清理 timeout/kill timer，最终由 pool drain 后释放 job 槽位。

### 队列无容量和公平性约束

**[中][confirmed]** `web/server/billing-export-jobs.ts::submitBillingExport` 对单 job 限制 200 个 task，却不限制每 owner 的 queued/running 数，也没有全局 backlog 上限。`web/server/db.ts::createBillingExportJob` 永久保留所有 queued/running/cancelling 记录；100 RPM 限速仍允许单账号在一分钟内入队近 100 个、合计近 20,000 次 Chrome 抓取，其他用户只能等待，DB 也会持续膨胀。

修复应在持久化入队的同一临界区检查容量，例如每 owner 最多 1 个 active、全局最多 N 个 queued，并对超限返回 409/429 和当前 active job。若允许多 owner 排队，应按 owner 轮转而不是纯 createdAt FIFO；提交接口还应支持幂等键或相同参数去重。

### 100 条历史裁剪会破坏完成文件的 TTL 承诺

**[中][confirmed]** `web/server/db.ts::createBillingExportJob` 每次创建任务都只保留最近 100 条终态记录，没有排除 `status === completed && expiresAt > now`。第 101 个终态 job 出现后，仍在 24 小时 TTL 内的 completed job 可能从 DB 消失；对应目录随后被 `sweepExpiredJobs` 当成 orphan，并按目录 mtime 超过一小时删除，实际保留期可能远短于界面展示的 `expiresAt`。

修复应把未过期 completed 视为不可裁剪，先由 sweeper 到期删除产物并转成 expired，再按审计保留策略裁剪 terminal metadata。若必须设置总记录硬上限，裁剪时应显式清理目录、记录 evicted 原因并让 API 返回可解释状态。

### TTL sweeper 与 Express 下载存在 TOCTOU

**[中][confirmed]** `web/server/billing-export-jobs.ts::getBillingExportDownload` 先 `existsSync` 返回路径，路由再 `statSync`、设置 `Content-Length`/ZIP 头并创建异步 read stream。定时 `sweepExpiredJobs` 可以在 createReadStream 真正打开 fd 前删除目录；stream error handler 此时可能在旧 ZIP Content-Type/Content-Length 下发送 JSON 500，或者在 headersSent 后直接销毁连接。`stream.pipe(res)` 也没有统一处理客户端断连与 source 销毁。

修复应把“校验状态 + 获取下载租约/打开只读 fd”做成一个操作：发送响应头前打开 fd 并用 fstat 取长度，活跃下载计数让 sweeper 延后删除，完成/断连后释放租约。路由使用 `stream.pipeline` 统一处理 source error、response close 和 fd 关闭；打开失败时先清除 ZIP 专用头，再发送 JSON 错误。

### 递归删除依赖未校验的持久化 job.id

**[中][confirmed]** `web/server/billing-export-jobs.ts::jobDir` 直接 `path.join(OUTPUT_ROOT, jobId)`，随后把结果传给 `cleanupWorkDir` 的 `fs.rmSync(..., { recursive: true, force: true })`。API 创建的新 ID 是 UUID，但 DB schema 只验证 `billing_export_jobs` 为数组，不验证每条记录；恢复旧备份、手工修复或数据损坏产生 `../` 值后，服务启动和每分钟 sweeper 都可能递归删除输出根目录之外的内容。

修复应在 DB normalization/recovery 时验证 job id 为严格 UUID，并在路径层用 `path.resolve` 检查结果前缀为 `resolvedRoot + path.sep`。所有读、写、rename 和 rm 都走同一个 safe-path helper；非法记录应隔离并告警，不能执行清理。输出根目录也应拒绝文件或符号链接并校验权限。

### 轮询在瞬时 HTTP 错误后静默冻结并消耗限速额度

**[中][confirmed]** `web/client/src/api.ts::request` 除 401 外不检查 `res.ok`，会直接返回 429/5xx 的 JSON。`web/client/src/pages/Billing.tsx` 的 polling effect 只在 `res.success` 且状态 active 时安排下一次 tick，因此 429、502 JSON 或临时 500 不会进入 catch，也不会重试或显示错误，页面会永久停留在旧进度。固定两秒轮询又让单标签页消耗约 30 RPM，四个标签页就超过 `web/server/index.ts` 的每 IP 100 RPM 全局限制。

修复应让 API helper 暴露 HTTP status 或对非 2xx 抛带 status 的错误。poller 对 5xx/网络错误做有上限的指数退避与 jitter、对 429 遵循 Retry-After、对 401/403/404/410 停止并刷新 UI；页面 hidden 时降频，恢复 visible 时立即刷新。基础间隔应结合全局限速预算，或把状态端点放到独立低成本 limiter/SSE 通道。

### 状态机和并发边界没有自动化测试

**[中][confirmed]** 仓库未找到 billing export 测试，`web/package.json` 也没有 test 脚本。owner/admin、queued-vs-running 取消、多个 worker drain、zip kill、重启恢复、100 条裁剪、TTL 下载竞态和轮询重试全部依赖人工推理。

修复应为 runner 注入临时 DB/output root、fake exporter 和可控 clock/process adapter，再补集成测试覆盖状态转换与授权端点。测试断言任何时刻最多一个 job 的 workers 存活、cancel 返回 terminal 前所有 child 已退出、重启后 queued 继续而 running/cancelling 变 interrupted、过期清理不会中断已有下载。
