# 账户清理器第二轮：删除门已关闭，但未来完成语义仍不安全

当前 `probe`、`scan`、`plan` 的可达 AWS 调用均为 AssumeRole、list/get/describe 类只读调用；`KNOWN_COVERAGE_GAPS` 恒非空，使 `verify.clean` 恒为 false，并让 `nuke` 在首轮 `delete_round` 前停止，因此当前代码不会产生资源写入。上一轮的 live Organizations 校验、嵌套栈/ServiceLinkedRole 识别、默认 VPC、CloudFront 和 KMS 问题已实质修复。实际 nuke 仍未获批：覆盖契约不是穷尽式，受保护 CloudFormation 后代会被当成可接受残留，所有权零匹配不 fail closed，且父作用域内唯一的资源会在 plan 前静默去重。Watch for: **[High][confirmed]** 清空已列 gaps 后仍可能在不完整清单上写入；**[High][confirmed]** protected stack 中的计费资源可形成假 complete；**[High][confirmed]** 已知 CFN 类型零匹配不会阻断同轮直接删除；**[High][confirmed]** EKS/EventBridge 重名资源可能在用户未看过的后续轮次被删除。

**Verdict**: NEEDS_CHANGES

## High-level view

只读 `probe`/`scan`/`plan` 可以在生产 EC2 上运行，但输出必须标为“不完整覆盖”，不能据此确认账号已清空。当前 `nuke` 是安全拒绝执行，不具备实际清理能力；未发现绕过 coverage gate 到达删除器的路径。

Organizations 保险丝已改为实时事实校验：映射 payer 必须是 live management account，目标必须是该组织的 ACTIVE member，并在每一删除轮与最终验收前重验。

CloudFormation 能建立嵌套关系并让成功匹配 owner 的资源只经 stack 删除。剩余风险是零匹配不报错，以及 protected stack 的任意后代都会进入 allowed residual。

生命周期跟踪仍缺 EKS 子资源和 DynamoDB 状态，普通 no-progress 阈值可能先于异步 deadline 停止；这是可恢复的提前终止，不会突破当前写入门。

## 当前 coverage gate 保证零写，但不能安全解除

`KNOWN_COVERAGE_GAPS` 在 `scripts/cleanup.py:48-63` 注入每次 inventory，`coverage_complete` 在 `scripts/cleanup.py:300-303` 要求 gaps 为空。`nuke` 于 `scripts/cleanup.py:2748-2763` 先检查 issues/coverage，写入口 `delete_round` 到 `scripts/cleanup.py:2793` 才出现；当前常量不变时，正确 `--confirm` 也只执行 STS、Organizations 和读取。`verify` 在 `scripts/cleanup.py:2680-2688` 同样把 coverage 纳入 `clean`。

**[High][confirmed]** 这不是可安全清空的覆盖契约。`KNOWN_COVERAGE_GAPS` 是手工否定列表，区域 scanner 列表在 `scripts/cleanup.py:947-974`，没有正向 manifest 证明每个 enabled region × 必需 scanner 都有记录，也未把 DocumentDB/Neptune、AWS Batch、EMR、Elastic Beanstalk、MSK、CodeBuild/CodePipeline 等资源族列为 scanner 或 gap。实现并移除当前 13 个字符串后，`coverage_complete` 仍可能在资源不可见时变 true。修复应逐区域校验 expected scanner set；所有尚无权威 enumerator/deleter 的服务必须继续产生 gap。

## Protected stack 后代被误当成完成态

**[High][confirmed]** `_scan_cloudformation` 在 `scripts/cleanup.py:1155-1186` 把含访问链 role 或任意 `AWS::IAM::ServiceLinkedRole` 的 stack 作为 protected seed，并向父子栈传播。`apply_resource_relationships` 在 `scripts/cleanup.py:1763-1769` 将其匹配到的所有物理资源标记 `preserve=managed_by_preserved_stack`；`classify_resource` 在 `scripts/cleanup.py:1807-1810` 把任何 preserve 对象变成 `allowed_residual`，verify/nuke final 又在 `scripts/cleanup.py:2680-2688, 2821-2830` 从 residual 排除它们。

包含 ServiceLinkedRole、负载均衡器、数据库或计算资源的 stack 因而可在 coverage 完整后报告 clean/complete。应拆分 `preserve_from_delete` 与 `allowed_residual`：后者只接受明确 allowlist 的访问链 IAM role/profile/必要 policy、默认 VPC baseline，以及没有其他残留后代的 stack shell；其余 protected 后代必须阻止完成并要求人工拆栈或迁移访问角色。

## CloudFormation 所有权只对成功匹配 fail closed

**[High][confirmed]** stack scanner 在 `scripts/cleanup.py:1202-1204` 无条件写 `ownership_complete=True`。未知 CFN type 会产生 issue，但已知 type 的 `physical_id` 在 inventory 中零匹配时，`scripts/cleanup.py:1735-1747` 不记录失败；只有一个 inventory key 出现多个 owner 才在 `scripts/cleanup.py:1753-1755` 报错。ID 表示变化、作用域歧义或 scanner 漏项时，stack 可先收到 DeleteStack，未标 `delete_via_stack` 的物理资源仍可同轮进入直接 deleter。

每个有 physical ID 的 mapped reference 都应要求 exactly one match；零匹配或多匹配均生成 blocking `ScanIssue`。`ownership_complete` 必须由匹配结果计算，匹配键优先使用 ARN 并包含 EventBridge bus、EKS cluster 等父作用域。

## 作用域内名称在 plan 前被折叠

**[High][confirmed]** `Resource.key` 在 `scripts/cleanup.py:247` 只含 service/type/region/resource_id，inventory 在 `scripts/cleanup.py:911-914` 按该 key last-write-wins。EKS node group、Fargate profile、addon 在 `scripts/cleanup.py:1263-1269` 只用 cluster 内唯一的名称；EventBridge rule 在 `scripts/cleanup.py:1305-1306` 只用 event bus 内唯一的名称。多个 EKS cluster 都有 `vpc-cni` addon 时，plan 只显示一个，nuke 删除后下一轮才暴露并删除另一个，实际删除超出已审阅计划；若可见副本进入 preserve，隐藏副本还可参与假 complete。

资源 identity 应使用 ARN 或复合 parent key；显示名称和 API 参数留在 metadata。相同 key 但 ARN/parent 不同必须生成 blocking duplicate-identity issue。

## 异步状态仍可能被 no-progress 提前截断

**[Medium][confirmed]** fingerprint 在 `scripts/cleanup.py:64-79, 308-311` 声明 EKS node group/Fargate profile 和 DynamoDB 状态参与进度，但 `_scan_eks` 在 `scripts/cleanup.py:1263-1269` 只记录 cluster，DynamoDB 在 `scripts/cleanup.py:1273-1274` 只记录 table name。循环在 `scripts/cleanup.py:2795-2801` 可在默认三轮后停止，早于 `scripts/cleanup.py:2774-2792` 的 async deadline。

补充 describe_nodegroup、describe_fargate_profile、describe_addon、describe_table 状态；`ASYNC_TYPES` 不应在 waiter/deadline 前受普通 unchanged 阈值终止。
