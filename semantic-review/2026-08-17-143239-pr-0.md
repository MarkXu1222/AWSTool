# AWS member-account cleanup CLI with incomplete destructive safety gates

The new CLI provides structured inventory, the requested admin credential paths, dependency-ordered deletion, and repeated account assertions. Read-only commands are separated from the confirmed `nuke` path, and direct references to the three access-chain roles are protected. The destructive admission gate and CloudFormation ancestry checks still permit deletion outside those intended safety boundaries, while incomplete dependency and inventory handling makes successful cleanup or verification unreliable.

Watch for: **confirmed** arbitrary assumable non-payer accounts can pass the destructive gate; **confirmed** nested CloudFormation deletion can remove a preserved access role; **confirmed** permissions boundaries prevent IAM cleanup; **confirmed** inventory blind spots can produce a false-clean verification; **confirmed** region discovery falls back to a partial destructive run; **confirmed** pending KMS deletion defeats no-progress termination; **likely** cyclic security-group references cannot be resolved.

**Verdict**: NEEDS_CHANGES

## High-level view

The credential chain follows the requested direct-admin then payer/OAAR order, but admission validates only ID shape and the payer blocklist. STS assertion proves the session reached the typed account; it does not prove that account is a managed member.

The scanner covers the named core services, but a region-discovery failure narrows destructive work to one region and several IAM/ECS/CloudFront resource classes are invisible. `verify` therefore cannot guarantee that every non-allowed residual is listed.

Direct access roles and default resources are preserved, but nested stack ownership, IAM permissions boundaries, security-group references, and seven-day KMS terminal states are not resolved safely by the deletion loop.

## Account assertion verifies identity but not organization membership

**Critical, confirmed:** `validate_target` checks only account-ID format and configured payer IDs (`scripts/cleanup.py:527-532`), then `assume_admin` tries direct `admin-console` before checking `accounts_cache` (`scripts/cleanup.py:663-680`). Any non-member account whose role trusts the base principal can reach `nuke`; STS assertions only reconfirm that same unintended account. Require a unique cache record with an exact configured `_payer` mapping before admin access to `scan`, `plan`, `nuke`, or `verify`.

## Nested CloudFormation stacks bypass access-role preservation

**Critical, confirmed:** protection inspects direct `list_stack_resources` children only (`scripts/cleanup.py:969-976`). A nested stack appears as `AWS::CloudFormation::Stack`, so its protected role is invisible to the parent check; unconditional parent deletion then cascades into the child (`scripts/cleanup.py:1480-1484`). Recursively propagate protection through nested-stack ancestors, or skip a stack tree whose ownership cannot be proven safe.

```
parent stack (deletable)
└── nested stack
    └── admin-console role (protected only on the child inventory item)
```

## IAM permissions boundaries survive every deletion round

**High, confirmed:** user cleanup never calls `delete_user_permissions_boundary` before `delete_user` (`scripts/cleanup.py:1836-1878`), and role cleanup omits `delete_role_permissions_boundary` (`scripts/cleanup.py:1895-1913`). Policies used as boundaries are incorrectly sent through attached-policy detach calls (`scripts/cleanup.py:1920-1939`). Boundary-bearing users, roles, and policies remain in conflict/failed states; remove boundaries explicitly without detaching policies required by preserved roles.

## Verify can report clean while in-scope resources remain

**High, confirmed:** IAM inventory stops at users, groups, roles, and local policies (`scripts/cleanup.py:1158-1177`), missing standalone instance profiles, virtual MFA devices, server certificates, and identity providers. ECS omits task definitions and custom capacity providers (`scripts/cleanup.py:989-1004`), while CloudFront lists distributions only (`scripts/cleanup.py:1178-1194`). Because cleanliness depends solely on this inventory (`scripts/cleanup.py:2001-2005`), these resources can survive a successful verification. Inventory them with automatic or manual dispositions, and add charge-bearing RDS Reserved DB Instances to the manual plan.

## Region discovery failure permits a partial destructive run

**High, confirmed:** failed `DescribeRegions` falls back to `config.region` plus an issue (`scripts/cleanup.py:762-776`), and `nuke` still deletes from that fallback inventory (`scripts/cleanup.py:2045-2052`). The command eventually reports incomplete, but only after unplanned partial deletion. Keep diagnostic fallback for read-only commands, but make `nuke` fail closed unless enabled-region discovery is authoritative.

## Pending KMS deletion never reaches a terminal loop state

**Medium, confirmed:** `PendingDeletion` is returned as `waiting/asynchronous` (`scripts/cleanup.py:1828-1831`), which resets the no-progress counter (`scripts/cleanup.py:2055-2062`), while final completion still requires the key to disappear (`scripts/cleanup.py:2082-2090`). A seven-day deletion window therefore forces the run to exhaust its default 40 rounds. Treat a confirmed schedule as terminal for `nuke` reporting while allowing later `verify` runs to show the pending key.

## Security-group references can deadlock VPC cleanup

**Medium, likely:** the deleter calls `delete_security_group` without revoking ingress or egress references (`scripts/cleanup.py:1731-1735`). Mutual references or references from a default group keep non-default groups in `DependencyViolation` and block VPC deletion. Revoke provable in-account group references first; report cross-account or uncertain references as residuals.
