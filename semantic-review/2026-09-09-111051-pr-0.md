# `admin-console` 单账户永久排除

这组改动为 `adminRoleExcludedAccounts` 建立了配置、StackSet 排除、自愈跳过、临时凭证拒绝和前端隐藏链路，目标是让账户 `227854707114` 只保留 `support-quota`。显式 Admin 临时凭证与显式 Admin 控制台已在服务端拒绝，Root AssumeRoot API 没有复用该门禁。当前实现仍有一个可获得管理员控制台会话的 `auto` 旁路，且健康状态无法证明既有 `admin-console` 已移除。

Watch for: **[confirmed, High]** 排除账户被改成单控制台按钮后请求 `auto` 模式，`support-quota` 不可用时仍回退到 payer 管理员链；**[confirmed, Medium]** 排除账户即使仍能 AssumeRole 到 `admin-console` 也会被记录为健康；**[confirmed, Medium]** 配置只验证 payer 名称存在，不验证账户实际归属，填错另一个有效 payer 会让 StackSet 排除落到错误组织；**[confirmed, Low]** 没有专项自动化回归测试。

**Verdict**: NEEDS_CHANGES

## High-level view

显式高权限入口通过账户 ID 集合拒绝排除项，但控制台兼容 `auto` 路径没有该门禁。前端因为 `_consoleDual` 被关闭而改走 `auto`，只读角色失败时仍可能获得 `OrganizationAccountAccessRole` 管理员会话。

Admin StackSet 将新名单与 `restricted_accounts` 合并并使用 `DIFFERENCE`，support StackSet 不受影响。配置中的 payer 只是筛选键而非已验证的组织归属，语法有效但归属错误的记录会让部署层与应用层执行不同策略。

自愈继续补齐 support 并跳过 Admin 补建，但 `support && (admin || adminExcluded)` 把“Admin 仍存在”也视为健康，无法观测必要的人工删除是否完成。

本地生产构建、服务端 TypeScript 编译和 `git diff --check` 均通过。`config.json` 已包含目标账户和 `yottahub-cma-1`，但本地 1,244 条账户缓存与角色记录均没有该账户，组织归属和 AWS 角色现状仍需在生产验证。

## 单按钮 `auto` 模式绕过 Admin 控制台拒绝

**[confirmed, High]** `listAccounts` 对排除账户设置 `_consoleDual: false`（`web/server/aws-service.ts:646-653`），`Accounts.ConsoleButton` 随后调用没有 `access` 参数的 `openConsole`（`web/client/src/pages/Accounts.tsx:257-261`）。路由把缺失或未知的 `access` 解析为 `auto`（`web/server/routes/aws.ts:669`），`getConsoleSigninUrl` 再调用 `assumeToAccount`（`web/server/aws-service.ts:1973-1975`）。该函数先尝试 `support-quota`，失败后使用 payer 管理凭证 AssumeRole 到目标账户的 `OrganizationAccountAccessRole`（`web/server/aws-service.ts:231-289`）；这条路径既没有 `isAdminRoleExcluded` 检查，也没有显式 Admin 模式的 `root_access` 门禁。

只要 support 角色暂时缺失、信任失败，或已被 `supportRoleUnavailable` 缓存为不可用，可访问账户页的普通已认证用户就可能从“控制台”按钮取得管理员会话。后端应对排除账户强制只允许 `access='support'`，前端也应为 `_adminRoleExcluded` 显式调用 `openConsole(accountId, 'support')`；隐藏入口不能代替服务端授权。

## 角色状态把仍存在的 Admin 当成合规

**[confirmed, Medium]** 自愈补建分组会跳过排除账户的 Admin，但最终健康条件是 `st.support && (st.admin || adminExcluded)`（`web/server/account-roles.ts:334-336`）。因此 `admin=false` 和 `admin=true` 都会得到 `state='ok'`、清零尝试次数且不告警，与 README 声明的健康形态 `support=true + admin=false + admin_excluded=true` 不一致。

新的 `DIFFERENCE` 目标不会自动删除既有 StackSet 实例，文档也明确要求单独执行 `DeleteStackInstances(RetainStacks=false)`。当前健康计算会掩盖该步骤未执行、执行失败，或角色日后被其他机制重建；应将排除账户仍可 AssumeRole 到 Admin 记录为策略违规，但无需让自愈自动删除角色。

## payer 字段没有验证目标账户归属

**[confirmed, Medium]** 三处解析只校验 `payer` 是否出现在 `config.payers`。StackSet 脚本按记录中的 payer 过滤（`web/scripts/setup-org-stacksets.ts:88-108, 253-255`），但 `account-roles.ts` 和 `aws-service.ts` 丢弃 payer 后仅按账户 ID 全局拒绝/跳过（`web/server/account-roles.ts:46-66`、`web/server/aws-service.ts:84-104`）。

若目标账户实际属于 payer A、配置却填写另一个有效 payer B，应用层仍会拒绝 Admin，自愈也不会补建，但 payer A 的 Admin StackSet 后续可以重建 `admin-console`。部署前应从目标 payer 的 Organizations 列表验证归属并 fail-closed，或至少核对账户缓存 `_payer` 并报告冲突。本地缓存找不到该账户，无法离线确认 `yottahub-cma-1` 是否为真实归属。

## 缺少跨入口和切换状态回归覆盖

**[confirmed, Low]** 这次改动没有新增测试，仓库也未找到 `account-roles` 专项测试。最低覆盖应验证排除账户的显式 Admin 凭证、显式 Admin 控制台和省略 `access` 的控制台请求都不能进入管理员链；support 控制台与 AssumeRoot 仍可用；自愈只补 support；payer 归属错误 fail-closed；非排除账户与 payer 管理账户行为不变。

上线前还需确认 `227854707114` 位于 `yottahub-cma-1`；以 `RetainStacks=false` 删除 Admin StackSet 实例；重新部署 Admin StackSet 后角色未重建；运行 support StackSet/自愈后 support 可 AssumeRole；Admin 临时凭证、显式 Admin 控制台和无 `access` 控制台都不能获得管理员会话；最后执行一个受控 AssumeRoot 操作确认 Root 链不受影响。
