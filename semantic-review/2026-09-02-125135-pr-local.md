# Billing export job hardening after first-pass review

This second pass rechecks the billing-job-scoped local diff against the first-pass findings. Queued cancellation, picker activation, bounded Blob fallback, split download auditing, and the concise live region are corrected; the 20-second timeout bounds Puppeteer connection startup. The directory lock closes the half-written-owner window, but stale-lock reclamation still permits two contenders to delete each other’s newly acquired lock, and graceful shutdown still does not own all pre-browser/launch cleanup.

Watch for: **confirmed High** — concurrent reclaimers of one stale lock can still start two runners; **confirmed Medium** — shutdown can finish before Puppeteer’s asynchronous launch-failure cleanup and cannot abort the federation-token fetch; **confirmed residual testing gap** — lifecycle invariants remain unautomated under the stated no-new-tests constraint.

**Verdict**: NEEDS_CHANGES

## High-level view

The new lock is an atomic directory with separate owner metadata, so a fresh ownerless directory is no longer reclaimed. Reclamation remains non-atomic: two processes can classify the same old directory as stale, then one can remove the other’s replacement while both retain logical ownership.

Puppeteer now gets 20 seconds to establish a browser, below the server’s 30-second shutdown deadline. That bounds launch rejection but not process cleanup: installed Puppeteer starts its launch-failure close callback without awaiting it, local code has no `Browser` handle until `launch()` resolves, and the preceding AWS federation `fetch()` is unbounded and receives no job abort signal.

The other requested boundaries are closed: cancellation persists `cancelled` before cleanup, the picker is the click handler’s first await, fallback downloads require a positive `Content-Length` no larger than 128 MiB, completion audit follows successful `pipeline()`, and the live region contains only status and phase.

## Stale-lock reclamation can still create two active runners — confirmed High

Once a lock is classified as stale, `web/server/billing-export-jobs.ts:499-512` inspects the shared path and later removes that path without proving it is still the same directory. Two processes starting against one old lock can interleave as follows:

```
process A                         process B
read old owner; PID is dead      read old owner; PID is dead
remove old directory
mkdir new lock; write owner A
                                  remove RUNNER_LOCK_PATH (now A's lock)
                                  mkdir new lock; write owner B
start runner A                    start runner B
```

Both return with `runnerLockHeld = true` and can process the same persisted queue concurrently. Reclamation needs an atomic claim over the stale directory itself—for example, renaming the observed lock to a unique tombstone and deleting only that tombstone—so only one contender can transition from stale observation to replacement.

## Shutdown remains detached from launch-failure and sign-in cleanup — confirmed Medium

The installed Puppeteer `BrowserLauncher` catches the 20-second timeout and invokes `void browserCloseCallback()` rather than awaiting browser-process closure. Because local `browser` is assigned only after `launch()` resolves (`web/server/billing-exporter.ts:361-386`), `captureOne()` cannot pass that startup process through `closeBrowserBounded()`; its promise can settle, `stopBillingExportRunner()` can return, and `index.ts` can call `process.exit()` while Puppeteer’s fallback close is still pending.

Shutdown can also block before Puppeteer starts. `captureOne()` awaits `getConsoleSigninUrl()` without forwarding its job signal (`web/server/billing-exporter.ts:356-359`), while that function performs `fetch(getTokenUrl)` with neither timeout nor `AbortSignal` (`web/server/aws-service.ts:1931`). Pass the job signal into sign-in acquisition and Puppeteer launch, and await termination of any process spawned during launch before releasing the runner lock.

## Lifecycle coverage remains a constrained residual gap — confirmed

No automated test file was added for runner locking, shutdown, cancellation, TTL leases, or owner authorization. Under this pass’s explicit constraint, this is residual risk rather than an additional change request and does not independently affect the verdict. Server and client TypeScript checks pass with `--noEmit`; `git diff --check` reports no scoped whitespace errors.
