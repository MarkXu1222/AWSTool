# Quick Setup 自动信任已移除，空 PhysicalResourceId 仍可绕过 Custom 阻断

最新版本删除了 Quick Setup template/code allowlist、provider 身份校验和 custom-resource trusted marker；带 `PhysicalResourceId` 的 `Custom::SSMLifecycleResource` 会进入 `UnsupportedCloudFormationType` issue。EventBridge 完整分页、Lambda/Event 服务级 NotFound 证明、Lambda Permission 精确 parent logical ID、nuke issue/gap 零写以及 Resource Explorer/SSM contract 均通过离线复查。仍有一个破坏阻断缺口：CloudFormation relationship pass 在判断类型前跳过空 `PhysicalResourceId`，因此创建中的 Custom resource不会产生 issue，所属 stack 仍可进入 `DeleteStack`。Python 3.9 grammar 检查通过，但当前机器没有 Python 3.9 解释器可做真实启动验证。

Watch for: **[High][confirmed]** 空 `PhysicalResourceId` 的非终态 Custom resource 绕过 `UnsupportedCloudFormationType`；**[Medium][confirmed]** 破坏性不变量仍无仓库级回归测试；**[Low][confirmed]** Lambda Permission 的 processed template 仍只接受 JSON。

**Severity**: Critical 0 / High 1 / Medium 1 / Low 1  
**Verdict**: NEEDS_CHANGES

## High-level view

Quick Setup 专用信任面已经关闭。`CFN_RESOURCE_TYPE_MAP` 没有任何 `Custom::*` 映射，relationship pass 对存在 physical ID 的 custom reference 生成 blocking issue；但 `if not physical_id: continue` 位于类型分派之前，使 `CREATE_IN_PROGRESS` 等尚未获得 physical ID 的 custom reference 完全不可见。

EventBridge inventory 与 CloudFormation stale-reference probe 共用显式 `NextToken` 循环。Lambda 只有 `GetFunction` 返回服务级 NotFound 才能标记 stale，Event rule 必须在完整枚举的每个 bus 上都由 `DescribeRule` 返回 NotFound；任一非 NotFound 错误都会使 scanner 失败。

Lambda Permission 只在 processed template 中的同 logical ID 资源确为 `AWS::Lambda::Permission`，且 `FunctionName` 通过 `Ref` 或 `Fn::GetAtt ... Arn` 精确指向同 stack 的唯一 Lambda logical ID 时，才被视为 stack-managed child。错误或无法解析的 parent 会生成 `UnprovenStackManagedChild`。

Resource Explorer 与 SSM 已进入 scanner manifest、覆盖矩阵、删除顺序和 deleter contract，botocore 1.42.68 的 operation shape 与 paginator model 均匹配。nuke 每轮在构造 deletable 和调用 deleter 前检查 issue 与 coverage completeness，离线 issue/gap 两条 trap 都保持零次删除调用。

Python 3.13 的 `ast.parse(..., feature_version=(3, 9))` 接受整个脚本，固定 boto3 1.42.68 下 `validate_runtime()` 也通过。缺少真实 Python 3.9 二进制和持久化测试意味着这些结果仍依赖一次性复审脚本。

## 空 physical ID 使 Custom resource 在类型门禁前消失

**[High][confirmed]** `apply_resource_relationships()` 对空 physical ID 直接 `continue`，`CFN_RESOURCE_TYPE_MAP` 的 unsupported 检查直到后面才执行（`scripts/cleanup.py:2129-2183`）。离线构造 `Custom::SSMLifecycleResource` + `CREATE_IN_PROGRESS` + 空 physical ID 后，issue 数为零，stack 仍分类为普通 delete；相同 reference 带 physical ID 时则正确返回 `UnsupportedCloudFormationType`。

这违反了“任何 `Custom::SSMLifecycleResource` 都必须阻断”的破坏性边界。扫描中的创建操作可能在扫描后获得 physical ID，而 `DeleteStack` 已可提交，重新进入 custom-resource 生命周期。应在空 physical ID 早退之前识别所有非终态 `Custom::*` 并生成 blocking issue；更保守的实现可以阻断所有缺少 authoritative absence proof 的未知非终态 CloudFormation type。

## Stale proof 与 Lambda Permission ownership 的信任边界

Event bus helper 消费所有 `NextToken`，并对重复 token 抛出 `CleanupError`（`scripts/cleanup.py:959-982`）；inventory 和 event stale probe 都调用该 helper。三页 fake client 确认请求序列为无 token、`t1`、`t2`，重复 token 和任一 bus 的 AccessDenied 都阻断扫描。

Lambda 只有 `GetFunction(FunctionName=physical_id)` 返回 NotFound 才写入 `confirmed_absent_by_api`；Event rule 在 default 与全部分页得到的 custom buses 上逐一执行 `DescribeRule`，每处都必须为 NotFound。relationship pass 不以 list omission 代替服务级 absence proof。

Lambda Permission template proof把 permission logical ID 回查到 processed template，再解析 `FunctionName` 的 `Ref` 或 `Fn::GetAtt`，并要求 stack summary 中恰有一个同 logical ID 的活跃 Lambda reference（`scripts/cleanup.py:1421-1473, 2147-2178`）。离线 exact-parent case 通过，指向 `OtherFn` 的 case 生成 `UnprovenStackManagedChild`。

## Coverage gate 与新增 scanner contract

`resource-explorer-2` 和 `ssm` 同时存在于 regional scanner IDs、resource-type manifest、CloudFormation ownership map、deletion order 和对应 deleter。固定 botocore 模型确认 `ListViews.Views`、`ListIndexes.Indexes`、`DeleteView.ViewArn`、`DeleteIndex.Arn`、`ListAssociations.Associations`、`DescribeParameters.Parameters`、`DeleteAssociation.AssociationId`、`DeleteParameter.Name` 均存在，四个 list/describe operation 也都有 paginator contract。

nuke 在每轮 scan 后立即检查 `inventory.issues or not inventory.coverage_complete`，早于 deletable 构造和 `delete_round()`（`scripts/cleanup.py:3291-3310`）。分别注入 scanner issue 与 coverage gap 的离线 trap 都得到 `blocking_scan_or_coverage_issues`、空 actions 和 `delete_round_calls=0`；final completion 也要求 issue 为空且 coverage complete。

**[Medium][confirmed]** 工作区没有 cleanup 专用测试文件。应把 Custom 空/非空 physical ID、EventBus 多页/重复 token、Lambda/Event NotFound 与非 NotFound、Permission parent mismatch、Resource Explorer/SSM model shape、issue/gap 零写和 Python 3.9 parse 固化为离线测试。

## Python 3.9 与 processed template 边界

脚本显式拒绝 Python 3.9 以下版本，源码通过 Python 3.9 feature-version AST，`str.removeprefix` 也从 3.9 可用；`validate_runtime()` 在 boto3 1.42.68 下通过。当前机器只有 Python 3.13.7，因此没有完成真实 Python 3.9 import/`--help` smoke test。

**[Low][confirmed]** 含 Lambda Permission 时，字符串形式的 processed template 只经过 `json.loads`（`scripts/cleanup.py:1426-1435`）。合法 YAML 会 fail closed 并永久阻断该 stack；应安全解析 YAML，或把 JSON-only 约束变成可验证的输入契约。
