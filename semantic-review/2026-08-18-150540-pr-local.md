# AWS quota synchronization connection lifecycle hardening

The change closes the production leak mechanism in the quota scheduler by bounding regional work and destroying every temporary Service Quotas client after success, error, or Abort. The same ownership pattern covers the STS clients used by `assumeToAccount`, and the region scheduler releases its per-account `AccountClient`. Return shapes remain compatible, but timeout-driven partial results can erase cached current values during enrichment. No Critical or High issue was found in the reviewed diff. **Watch for:** **confirmed, Medium** — the 15-second enrichment deadline converts unfinished lookups to persisted `null`; **confirmed, Medium** — STS, `listServiceQuotas`, and `AccountClient` operations still lack explicit deadlines; **confirmed, Low** — unexpected worker rejection makes `mapWithConcurrency` return before sibling workers finish; **confirmed, Low** — the lifecycle behavior has no regression tests.

**Verdict**: APPROVED

## High-level view

The original `268 accounts × ~34 regions` accumulation path is closed. `listQuotaRequests` limits each account to six regional clients, so the scheduler batch size of eight bounds normal Service Quotas concurrency at roughly 48 clients, and completed clients cannot survive into later batches.

`withAwsClient` destroys STS and single-region Service Quotas clients only after the awaited operation or pagination loop settles. This preserves response consumption but still depends on requests settling when no Abort signal is supplied.

Bedrock retains explicit per-region partial-success reporting and adds bounded concurrency and Abort. Quota history silently treats failed regions as empty, while enrichment silently converts timed-out current-value lookups to missing values that the scheduler persists.

Static server type checking passes. No tests cover client destruction, concurrency limits, Abort behavior, partial-result semantics, or scheduler cleanup.

## Temporary client ownership removes the completed-socket leak

`withAwsClient` at `web/server/aws-service.ts:65-73` awaits the operation and invokes `destroy()` from `finally`. The STS paths at `aws-service.ts:105-113`, `130-137`, `172-175`, and `184-187` release their keep-alive agents after AssumeRole succeeds or rejects; destroying the client after the response arrives does not invalidate the returned credential values.

`listServiceQuotas` owns one client through all pagination and releases it at `aws-service.ts:604-616`. Bedrock, quota-history, and enrichment workers release one client per region at `aws-service.ts:767-770`, `869-872`, and `924-927`. **Confirmed:** no normal success, SDK error, or explicit Abort path in this quota call chain leaves a completed temporary Service Quotas client alive.

## Six-worker regional fan-out bounds scheduler sockets

`mapWithConcurrency` at `aws-service.ts:77-95` assigns every input once, preserves result order, and caps active workers at six. Combined with the scheduler batch size of eight at `scheduler.ts:119-126`, `listQuotaRequests` reaches at most about 48 simultaneous regional clients rather than roughly 272.

**Confirmed, Low:** fail-fast `Promise.all` rejects as soon as one worker loop throws while sibling loops continue. Current Bedrock and quota-history workers catch expected SDK failures, and every created client still has `finally` cleanup, so this does not recreate the normal leak. An unexpected enrichment or processing exception can nevertheless let the caller advance while old workers are active; wait for all loops to settle before rethrowing.

## Bedrock, history, and enrichment expose different partial-result semantics

Bedrock's 15-second timer covers a region's full pagination loop rather than each page. A timeout records a regional error and may leave already collected rows in the response. Region deduplication and the new 30-region cap are applied before any clients are created at `aws-service.ts:712-714`.

`listQuotaRequests` gives each regional history call an eight-second deadline at `aws-service.ts:851-872`. It returns successful regions in input order but converts unavailable, timed-out, and failed regions to empty arrays; an all-region outage remains indistinguishable from an account with no requests.

**Confirmed, Medium:** `enrichCurrentValues` starts one 15-second timer for all sequential `GetServiceQuota` calls in a region at `aws-service.ts:898-918`. After it fires, the current and all subsequent calls use an already-aborted signal and become `null`, without an error or partial marker. `syncQuotaRequests` persists that value at `web/server/scheduler.ts:153-164`, so many unique requests or transient slowness can erase previously cached current values even though history synchronization succeeded. Preserve the prior value on lookup failure, report regional partialness, or use bounded per-lookup deadlines before persisting.

## Non-Abort operations can retain in-flight clients

**Confirmed, Medium:** `withAwsClient` reaches `destroy()` only after its operation settles. The installed Smithy Node HTTP handler defaults `requestTimeout` to zero and supplies no connection or socket timeout; STS AssumeRole at `aws-service.ts:105-187` and `listServiceQuotas` at `aws-service.ts:602-616` pass no Abort signal. A stalled request therefore retains its client and blocks that call indefinitely. `quotaSyncRunning` prevents repeated scheduler overlap, so this cannot reproduce the thousands of completed keep-alive clients from the incident, but it remains an unbounded in-flight retention path.

The region scheduler destroys `AccountClient` at `scheduler.ts:246-261` after all 17 regional status sends settle. **Confirmed, Medium:** those sends also lack a finite deadline, so one stalled send blocks `Promise.allSettled` and delays cleanup for the per-account client. Apply the same bounded request policy to STS, single-region quota, and Account operations.

## Incident behavior has no automated regression guard

**Confirmed, Low:** no existing tests reference `mapWithConcurrency`, the affected quota functions, client `destroy()`, or scheduler region cleanup. Type checking cannot verify cleanup exactly once on success/error/Abort, the six-worker ceiling, fail-fast overlap, or safe persistence of partial enrichment. Focused mocked-client tests can cover these without live AWS calls.
