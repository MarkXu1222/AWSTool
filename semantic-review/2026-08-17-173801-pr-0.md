# Coverage contract v3 的 scanner 与 CloudFormation 所有权门禁

v3 把 scanner ID、产出类型、删除顺序和 handler 绑定成启动校验，并补入 Resource Explorer、SSM Association 与部分 CloudFormation 非独立资源。结构不变量、新 API shape 和 issue/gap 零写门禁均通过本地验证。新的 CloudFormation 宽免却把“scanner 成功”当成“资源权威不存在”，并用普通模板即可满足的条件信任 Quick Setup custom resource，因此不能沿用上一版 APPROVED 结论。

Watch for: **[High][confirmed]** zero-match 会在 scanner complete 时静默变成 confirmed absent；**[High][confirmed]** Quick Setup 信任条件不证明 StackSet/AWS provenance；**[Medium][confirmed]** 任意同栈 Lambda 都能为 Permission 放行；**[Medium][confirmed]** v3 安全不变量仍无自动化测试；**[Low][confirmed]** 合法 YAML TemplateBody 会被当作无效 JSON。

**Severity**: Critical 0 / High 2 / Medium 2 / Low 1  
**Verdict**: NEEDS_CHANGES

## High-level view

`SCANNER_RESOURCE_TYPE_MANIFEST` 覆盖全部 scanner ID，`_collect` 拒绝未声明产出，`validate_runtime` 对 83 种声明类型中的自动类型逐一要求删除顺序和 callable handler。本地校验为零缺失；这保证结构接线，不证明 scanner 枚举完整或 handler 语义安全。

Resource Explorer 与 SSM Association 的本地 botocore shape、参数名和 Region 使用正确；view-before-index 顺序及 index async deadline 也匹配服务生命周期。`get_template`/模板 shape 错误会使 CloudFormation scanner failed，而不是继续删除。

CloudFormation zero-match 失去上一版 exactly-one 的 fail-closed 性质。scanner complete 只说明枚举未报错，不证明 identity alias 正确或 physical ID 已不存在；Quick Setup 与 Lambda Permission 例外又允许未进入独立 inventory 的对象跳过 unsupported-type issue。

`nuke` 在每轮写入口前重验 live member/payer 与 STS identity，并在任意 issue 或 coverage gap 时 break。issue-only 和 gap-only 内存 inventory 的 `delete_round` trap 调用均为 0；保护角色、KMS、默认 VPC、payer/member 与 Python 3.9 兼容未见 v3 回归。

## Scanner complete 不能证明 physical resource 已不存在

**[High][confirmed]** mapped reference 零匹配时，只要负责该类型的任一 scanner 在对应 Region 为 `complete`，代码就写入 `confirmed_absent_owned_resources` 并跳过 `CloudFormationReferenceMatchCount` issue（`scripts/cleanup.py:2111-2125`）。但 `complete` 只代表 scanner 返回且产出类型未越过 manifest（`scripts/cleanup.py:1110-1130`），没有 physical-ID existence probe 或 identity-normalization 验证。

内存复现保留一个真实 DynamoDB ARN/name inventory item、故意漏掉 `identity_aliases`，同时提供 physical ID `ExpectedTable` 和 complete coverage。结果为零 issue、reference 被记为 confirmed absent、table 未标记 `delete_via_stack`；nuke 会先触发 stack 删除，再按陈旧 inventory 独立删除 table。若零匹配来自漏枚举，stack 消失后该资源还能逃过 verify。应恢复 zero-match blocking，除非每种 mapped type 都能区分权威 not-found 与 access/shape/alias 错误。

## Quick Setup 白名单没有建立供应方信任

**[High][confirmed]** custom resource 的信任条件只有 stack name 前缀、精确 resource type/logical ID，以及 `ServiceToken` 指向同模板 `SSMLifecycleOperatorLambda.Arn`（`scripts/cleanup.py:1361-1409`）。代码不校验 StackSet instance、Quick Setup 配置身份、provider Lambda 来源或模板指纹。

普通模板可复用这些名称和内部连线，让任意 provider 驱动的 `Custom::SSMLifecycleResource` 进入 `stack_managed_non_inventory_resources`，绕过 `UnsupportedCloudFormationType` issue（`scripts/cleanup.py:2069-2106`）。该白名单必须绑定可验证的 AWS StackSet/Quick Setup provenance；模板自洽不等于来源可信。

## Lambda Permission 的 parent proof 不绑定目标函数

**[Medium][confirmed]** BucketPolicy 要求 physical ID 与同栈 bucket 相等，但 Lambda Permission 只要求同栈存在任意非删除 Lambda reference（`scripts/cleanup.py:2079-2094`）。内存复现中，一个 `decoy` Lambda 足以让任意 statement physical ID 零 issue 进入 stack-managed 清单。

应从 processed template 解析 Permission 的 `FunctionName`，证明 `Ref`/`Fn::GetAtt`/ARN/Sub 最终指向同栈、已枚举的具体 Lambda；无法解析时继续 blocking，避免 Retain 或异常删除后失去独立验收依据。

## 新 scanner 正确，但模板格式存在 fail-closed 可用性缺口

Resource Explorer 的 `ListViews.Views`、`ListIndexes.Indexes[].Arn/Type`、`DeleteView(ViewArn)` 和 `DeleteIndex(Arn)` 与本地 service model 一致；index 是异步后台删除，当前 view-before-index 与 async deadline 配置正确（`scripts/cleanup.py:1442-1473, 2453-2470`）。SSM Association 使用分页结果中的 `AssociationId` 并按 ID 删除，`AssociationDoesNotExist` 进入 not-found 幂等分类（`scripts/cleanup.py:1609-1641, 2642-2649`）。

`get_template` ClientError、缺失 resource map、错误 provider type 和错误 ServiceToken 都会使整个 CloudFormation scanner failed。**[Low][confirmed]** 字符串 `TemplateBody` 只走 `json.loads`，而 CloudFormation 支持 YAML；命中该分支的合法 YAML 会被报告 invalid JSON（`scripts/cleanup.py:1373-1387`）。这不会 fail open，但会持续阻断清理。

## Manifest 接线无法替代破坏性回归测试

本地 `validate_runtime` 验证 83 种声明类型零缺失 order/handler，`ast.parse(..., feature_version=(3, 9))` 通过。**[Medium][confirmed]** 工作区仍没有 cleanup 专用测试，上一版唯一 concern 未关闭；v3 需要覆盖 manifest drift、Resource Explorer/SSM shape、zero-match alias、stack-managed provenance、template failure、issue/gap 零写，以及 preserved-role/KMS/default-VPC/member gate。

`command_nuke()` 的 issue/gap 分支位于 deletable 构造和 `delete_round` 之前（`scripts/cleanup.py:3195-3267`），两类内存 trap 均验证零调用。v3 未改变 protected-role/CloudFormation closure、KMS replica-first 与完整 inventory guard、默认 VPC exact baseline、payer blocklist 或 live Organizations member 验证。
