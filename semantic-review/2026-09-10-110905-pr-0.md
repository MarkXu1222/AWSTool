# Dashboard operational detail and assignable Ops access

This change expands the Dashboard with account composition and actionable operational summaries while promoting Ops from an admin-only special page to an explicitly assignable sensitive page. The Dashboard additions reuse data already loaded by the page and introduce no Cost Explorer dependency; the Ops path is gated consistently from user defaults through menu rendering and the database-backed API guard. Admins retain access, non-admins require a stored `ops` page grant, and a stale admin claim in an old JWT cannot authorize fresh `/api/ops` reads after demotion. The blocking gap is that unavailable or never-collected Dashboard inputs are rendered as successful zero/healthy states.

Watch for: **confirmed** — a never-run role scan can produce “账户权限…均正常”; **confirmed** — failed Dashboard requests collapse into zero/blank/healthy output; **confirmed** — no automated regression tests cover the new Dashboard states or Ops permission matrix.

**Verdict**: NEEDS_CHANGES

## High-level view

The account structure panel derives its totals, active ratio, and payer ranking from the existing `listAccounts()` response. The pending-work panel derives rows from already-loaded role, connection, quota, and departed-account state. No new request or Cost Explorer path is introduced; the existing connection check still performs STS calls, while the account endpoint can fall back to Organizations on a cold server cache.

**Confirmed:** the new panels model loading but not source validity. Once requests settle, defaults become indistinguishable from successful zero results, and the empty-state copy asserts that permissions, connections, and quotas are normal when a source was unavailable or intentionally omitted as unknown.

Ops remains fail-closed for legacy non-admin users because only an actual `allowed_pages` array containing `ops` passes the backend guard. `/auth/me` reads the current database role and resolves legacy null to regular pages only, while `/api/ops` independently re-reads the user and validates both ID and username.

The menu and direct-route checks use the same admin-or-explicit-grant rule as the API. An old JWT remains cryptographically valid until expiry, but its embedded admin role no longer grants `/api/ops`; database-backed authorization revokes new Ops reads immediately after demotion.

## Existing Dashboard data reused without Cost Explorer

The effective data flow remains:

```text
listAccounts ───────────────► account KPI + account structure
getDashboardSummary ────────► role/quota/departed KPIs + pending-work rows
testConnection ─────────────► connection KPI + pending-work row
getQuotaStats ───────────────► seven-day Case KPI
```

`/api/aws/dashboard/summary` reads role summaries, quota records, and departed-account state from process/database data, and the codebase has no Cost Explorer client reference. `listAccounts()` is client-cached for one minute and normally served from the server account cache; an empty server cache can still trigger STS/Organizations, but the new panel does not add another call.

The added pending-work controls are native buttons with keyboard focus styling, and organization bars are decorative while counts remain text. **Confirmed:** an empty or failed account load leaves the organization caption followed by no rows and provides no “no data” explanation; this is part of the source-state collapse above.

## Unknown role status is announced as healthy

**Confirmed:** `getDashboardLiveCounters()` deliberately omits `roleIssues` when no role scan has ever run. The client excludes the role issue row, but the fallback checks only `attentionItems.length === 0` and then states that “账户权限、组织连接和配额状态均正常.” A fresh deployment can therefore assert normal account permissions without evidence. The empty state must treat absent role data as unverified or avoid the all-normal claim until `roleIssues` is present.

## Request failures collapse into zero and blank output

**Confirmed:** Dashboard request failures are swallowed. `ready` becomes true after account/quota requests settle regardless of success; `summaryLoading` and `connLoading` become false after rejected requests while defaults remain zero. The account structure then renders `0%` and a blank organization list, and pending work can show the same all-normal message used for verified healthy data. Transport failure, intentional unknown, and confirmed zero need distinct states.

## Ops grant, legacy behavior, and stale-token revocation

The backend default set excludes `ops`, while `ALL_PAGE_KEYS` includes it for normalization and assignment. Admins resolve to all pages; legacy non-admin null resolves to regular pages only; new non-admin forms start from that same set. The API guard requires a persisted array explicitly containing `ops`, so null cannot become an implicit grant.

`MainLayout` hides Ops before `/auth/me` resolves, permits it for the current database admin role or an explicit returned grant, and applies the same check before mounting `/ops`. The API guard re-reads the user on every request, matches token identity to the database record, and ignores the JWT role claim for authorization. Demotion or grant removal blocks the next `/api/ops` request even though the two-hour JWT itself remains valid.

## Validation and missing regression coverage

`git diff --check`, the Vite production build, and `tsc -p server/tsconfig.json --noEmit` pass. The build produces the lazy Ops chunk and retains the existing large-chunk warning.

**Confirmed:** the diff adds no automated tests for the permission matrix or Dashboard state transitions. Coverage should include admin access, non-admin explicit grant, legacy null, grant removal/demotion with an old token, no role scan, rejected summary/connection/account requests, and a genuine empty account result.
