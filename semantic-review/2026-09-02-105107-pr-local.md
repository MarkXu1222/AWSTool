# Excel-driven account selection for bulk billing PDF exports

This change adds browser-local `.xlsx` account discovery to the existing billing export form without changing the billing API contract. It parses every worksheet, extracts digit-bounded 12-digit IDs, de-duplicates them, intersects them with the loaded platform accounts, and replaces the account selection only when the intersection is non-empty. The selection and month behavior match the requested workflow, and the package API is compatible with the implementation. The input limits do not fully bound browser resource consumption because workbook expansion and parsing happen before the 50,000-cell check.

Watch for: **confirmed, Medium** — a ≤5 MiB compressed workbook can expand into very large worksheet XML and consume substantial browser memory/CPU before the scanner reaches its 50,000-cell rejection.

**Verdict**: NEEDS_CHANGES

## High-level view

The importer is isolated behind a dynamic browser-only dependency. It scans the `Sheet[]` returned by `read-excel-file@9.3.10`, recognizes only 12-digit sequences that are not part of a longer digit run, preserves first-seen order while de-duplicating, and exposes scan metadata for the UI summary.

The billing form computes the intersection against the currently loaded account list. A non-empty intersection replaces the selected accounts, while no detected IDs or no matches leave the prior selection intact; the upload handler does not mutate `selectedMonths`, and no uploaded file or extracted ID is sent to a new backend endpoint.

The compressed file-size check runs before parsing, but the cell-count check runs only after `readXlsxFile(file)` has unpacked and parsed every worksheet. Consequently, neither limit prevents a small, highly compressible workbook from causing excessive client-side work before rejection.

## Workbook expansion precedes the protective cell limit

**Confirmed, Medium:** `scanAccountIdsFromXlsx()` checks `file.size` and then awaits `readXlsxFile(file)` at `web/client/src/utils/account-import.ts:29-34`; it does not start counting represented cells until the dependency has returned all parsed sheets at lines 40-44. The browser entry expands accepted worksheet XML entries and materializes the complete `Sheet[]` before resolving, so a workbook containing millions of highly compressible cells—or oversized shared-string/worksheet XML—can allocate and parse far more than the intended 50,000-cell budget.

```text
≤5 MiB compressed XLSX
        |
        v
unpack accepted XML + parse every worksheet
        |
        v
count rows and reject after 50,000 represented cells
```

A crafted or accidentally oversized workbook can stall or crash the tab before the user receives the limit error. Add a pre-parse bound on total and individual uncompressed ZIP entry sizes, then use parsing that can stop as the cell threshold is crossed; moving work to a worker can protect responsiveness but does not by itself bound memory.

</details>
