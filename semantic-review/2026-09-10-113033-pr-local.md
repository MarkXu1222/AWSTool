# Assignable Ops access and failure-aware dashboard

This change moves Ops Monitor into the normal page-permission model while keeping legacy and new non-admin users default-denied. It hardens user-management endpoints so a demoted administrator cannot use an unexpired admin JWT to restore permissions. The Dashboard now distinguishes successful zeroes from loading, unavailable, and unverified states without adding Cost Explorer calls. Both previously reported blockers are resolved.

Watch for: **confirmed, non-blocking** — no automated test script covers permission transitions or Dashboard state rendering; validation is currently static plus build/type checks.

**Verdict**: APPROVED

## High-level view

Ops access uses `allowed_pages` end to end. `ops` is assignable but absent from legacy/new non-admin defaults; Settings, `/api/auth/me`, navigation, and `/api/ops` all apply the same explicit-grant rule.

User-management authorization no longer trusts `decoded.role`. List/create/update/delete/reset-password require the JWT user ID and username to match a current database administrator, closing the stale-admin self-grant path.

Dashboard sources have separate loading/success/error states. Request failures render unavailable, empty connection results and absent role checks render unverified, and successful zeroes remain distinct.

## Stale administrator tokens cannot restore Ops access

`isCurrentAdmin` loads the JWT subject by username, requires the persisted ID and username to match, then checks the current role. All five user-management endpoints use it, so a token issued before demotion receives `403` and cannot add `ops`, re-elevate a role, or grant another sensitive permission.

The Ops boundary independently binds the token to the current database user and reads persisted `allowed_pages`. This is **confirmed** in `web/server/auth.ts`, `web/server/ops-monitor.ts`, and the middleware order in `web/server/index.ts`; no stale-role trust remains on the reviewed self-grant path.

## Ops grants stay aligned across backend and UI

Administrators receive all assignable pages; non-admin users receive Ops only when persisted `allowed_pages` contains `ops`. `DEFAULT_PAGE_KEYS` omits Ops, `ALL_PAGE_KEYS` permits explicit assignment, Settings defaults and legacy edit fallbacks omit it, and `MainLayout` mirrors the API result. Direct URL entry remains subject to `requireOpsAccess`. Bulk quota correctly remains outside this model under `bulk_quota_access`.

## Dashboard separates zero, unavailable, and unverified

Accounts, quota statistics, operational summary, and connection checks are tracked independently. Failures gate their dependent metrics; missing `roleIssues` after a successful summary and an empty successful connection response are not painted healthy. The attention candidates are explicitly `Array<AttentionItem | null>` before narrowing, resolving the prior client type error.

The healthy-empty view appears only after accounts, summary, and connection requests complete without failure, unverified data, or actionable conditions. A failed retry cannot repaint retained values as current success because rendering is gated by current status.

## Validation boundary

`npm run build`, server TypeScript compilation, `npx tsc -p client/tsconfig.json --noEmit`, and `git diff --check` passed. The only residual risk is **confirmed, non-blocking**: `web/package.json` has no test script, so downgrade and Dashboard response matrices are not executable regressions yet.
