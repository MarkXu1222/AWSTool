# 服务级 absence proof 与 Quick Setup provenance 加固复审

最新版本移除了用 scanner complete 为 CloudFormation zero-match 放行的路径，改为仅接受 Lambda `GetFunction` 或 EventBridge `DescribeRule` 的服务级 NotFound，并从 processed template 精确解析 Lambda Permission 的目标 logical ID。Lambda absence proof 与 Permission decoy 修复成立，但 EventBus 枚举只读取第一页，仍可把后续页中的规则误判为不存在。Quick Setup 新增了固定模板 SHA-256、标签、provider 类型与 ServiceToken 校验，但这些证据仍可被目标账户内的调用方复制或漂移，未证明 AWS Quick Setup/StackSet 来源。

Watch for: **[High][confirmed]** `ListEventBuses` 的 `NextToken` 被通用 fallback 忽略，EventBridge zero-match 仍会 fail open；**[High][confirmed]** 固定模板与普通 stack tags 不证明 StackSet lineage，也不校验当前 provider Lambda 代码；**[Medium][confirmed]** 破坏性安全不变量仍无仓库级回归测试；**[Low][confirmed]** 合法 YAML `TemplateBody` 仍被 JSON-only parser 阻断。

**Severity**: Critical 0 / High 2 / Medium 1 / Low 1  
**Verdict**: NEEDS_CHANGES

## High-level view

zero-match 现在只有 `confirmed_absent_by_api` 才能绕过 exactly-one ownership match，scanner complete 已不再参与。Lambda 路径 fail closed；EventBridge 意图遍历全部 bus，但 botocore 1.42.68 没有 `ListEventBuses` paginator，而通用 fallback 不消费返回的 `NextToken`。

Lambda Permission 从 `FunctionName.Ref` 或 `Fn::GetAtt(..., Arn)` 得到具体 logical ID，并要求同栈恰有一个未删除的 Lambda reference；上一报告的 decoy-parent Medium 已关闭。不能静态解析的表达式继续产生 ownership issue。

Quick Setup 的 canonical SHA-256 对 JSON key 顺序和空白稳定，但 hash 和 tags 只证明模板形状；代码没有验证 StackSet/Quick Setup lineage 或已部署 Lambda 的 `CodeSha256`。复制 allowlisted 模板、伪造标签并在部署后替换 provider code 的 stack 仍可通过。

`command_nuke()` 在构造 deletable 和调用 `delete_round` 前检查 issues 与 coverage。两个离线 trap 均得到 0 次写路径调用，Python 3.9 feature AST 解析通过；复审未读取 `config.json`/`data/db.json`，未调用 AWS。

## EventBus 的第二页可重新打开 zero-match

**[High][confirmed]** `reference_confirmed_absent()` 通过 `paginate(events_client, "list_event_buses")` 构造 bus 集合，再逐个执行 `DescribeRule`（`scripts/cleanup.py:1342-1372`）。本地 botocore 1.42.68 显示该 API 输入与输出都有 `NextToken`，`Limit` 最大 100，但 `can_paginate("list_event_buses")` 为 false。通用 `paginate()` 捕获 `OperationNotPageableError` 后只调用一次 operation，不读取返回 token（`scripts/cleanup.py:954-959`）；离线 fake 返回 `NextToken="more"` 时也只有 1 次调用。

若目标 rule 位于第二页 EventBus，CloudFormation ownership lookup 与 `_scan_eventbridge()` 会同时漏掉它；absence probe 在第一页 bus 上全为 NotFound 后返回 true，`apply_resource_relationships()` 随即跳过 zero-match issue（`scripts/cleanup.py:2238-2247`）。nuke 的零写门禁因此看不到 issue，residual rule 还可能逃过 verify。应为 `ListEventBuses` 实现显式 `NextToken` 循环，并让 inventory scanner 与 absence probe 共用完整枚举器。

API 错误分类没有扩大放行面：本地 model 中 `GetFunction` 的 absence error 是 `ResourceNotFoundException`，`DescribeRule` 的 errors 是 `ResourceNotFoundException` 与 `InternalException`；当前代码只有 NOT_FOUND 返回 true，其他 ClientError 重新抛出，BotoCore errors 使 scanner failed。缺口来自 bus 集合不完整。

## Quick Setup 模板身份仍不等于供应方身份

**[High][confirmed]** `trusted_provenance` 要求 canonical hash 命中 allowlist，并匹配 Quick Setup document、版本、manager region/ID、definition ID 标签，随后检查 provider type 和 ServiceToken（`scripts/cleanup.py:1472-1509`）。这些 stack tags 没有 `aws:` 保留前缀，目标账户调用方可以设置；固定模板也可以复制。

CloudFormation template hash 不反映部署后通过 Lambda API 替换的函数代码。攻击者可部署 allowlisted 模板与标签，再修改 `SSMLifecycleOperatorLambda` 的实际代码，processed template 仍保持原 hash。删除 stack 时 CloudFormation 会调用当前 provider，而 scanner 没有检查 StackSet instance lineage、Quick Setup 配置身份或 provider `CodeSha256`。应从权威管理面验证预期 Quick Setup StackSet instance，并把当前 provider function/version 的不可变代码身份纳入 allowlist；否则继续把 custom resource 作为 blocking issue。

## Lambda Permission 已绑定具体函数，但模板解析仍只接受 JSON

Permission 校验从对应 logical resource 的 `Properties.FunctionName` 读取 `Ref` 或两种 `Fn::GetAtt` 形式，再要求同 logical ID 的 Lambda reference 恰好一个且未删除（`scripts/cleanup.py:1441-1470, 2187-2198`）。普通同栈 decoy Lambda 无法再满足条件；无法证明的表达式不会获得 trusted marker，后续转为 `UnprovenStackManagedChild`。

**[Low][confirmed]** `GetTemplate(TemplateStage="Processed")` 返回字符串时仍只执行 `json.loads`（`scripts/cleanup.py:1423-1438`）。合法 YAML 会使 scanner failed；这不会触发写入，但会阻断清理。应安全解析 YAML，或把受信来源明确约束为已验证的 JSON-only contract。

## 零写保险丝没有持续回归保护

issue/gap 检查位于每轮 scan 之后、deletable 构造和 `delete_round` 之前（`scripts/cleanup.py:3330-3346`）。离线替换 scanner 与 deleter 后，两类 inventory 都以 `blocking_scan_or_coverage_issues` 退出，trap deleter 调用数均为 0；最终 completion 也要求无 residual、无 issue 且 coverage complete。

**[Medium][confirmed]** 工作区仍没有 cleanup 专用测试文件。应提交离线测试覆盖多页 EventBus、Get/Describe 非 NotFound、Lambda logical-ID binding、伪造 Quick Setup provenance、provider code drift，以及 issue/gap 的零写保险丝；在这些测试存在前，不应解除相关 coverage gap。
