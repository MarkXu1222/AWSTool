# Durable background queue for AWS billing PDF exports

This change replaces the synchronous billing export response with a persisted JSON-backed queue, a single active runner, owner/admin-scoped job APIs, cancellable Chrome/zip work, TTL-retained artifacts, and resumable UI polling. It also adds graceful PM2 shutdown, explicit billing audit actions, and browser-side streamed downloads where the File System Access API is available. The lock acquisition protocol has a confirmed race that can activate two runners and undermine the single-instance guarantee.

Watch for: **confirmed High** — a contender deletes a newly created but not-yet-populated runner lock; **confirmed Medium** — shutdown cannot interrupt Chrome launch, queued cancellation depends on cleanup succeeding, Chromium's save picker can lose user activation, non-Chromium downloads buffer the whole ZIP, and the lifecycle has no automated tests; **confirmed Low** — download auditing precedes transfer completion and the polling UI live region can repeatedly announce progress.

**Verdict**: NEEDS_CHANGES

## High-level view

The queue persists tasks, progress, per-item results, ownership, terminal states, and artifact metadata in `db.json`, while a process-local runner executes one job at a time. The cross-process guard is unsafe during simultaneous startup: a process that observes the lock between creation and payload write treats it as stale and removes it, allowing both processes to run the same queue.

Cancellation reaches capture waits, active browsers, the worker pool, and zip through an `AbortController`, but only after `puppeteer.launch()` resolves. PM2's 30-second hard shutdown boundary can therefore terminate Node before a stalled launch enters bounded cleanup; queued cancellation also leaves the job runnable when directory cleanup fails.

Authorization is re-read from the database, new jobs use stable user IDs, admins may inspect all jobs, and the UI only auto-restores jobs marked as owned by the current user. TTL cleanup uses in-memory download leases so an already-open stream survives expiry, but browser downloads remain memory-bounded only in Chromium and its picker is invoked after a network await that can consume transient activation.

Polling has a 15-second request deadline, exponential retry, `Retry-After`, and visibility-aware cadence. The concurrency and cleanup invariants have no automated coverage, while audit and accessibility behavior remains inaccurate/noisy at transfer and polling edges.

## Half-written lock files can produce two active runners — confirmed High

`acquireRunnerLock()` creates `.runner.lock` with `openSync(..., 'wx')` and then writes the PID. A second process can observe `EEXIST` in that interval, fail to parse the empty or partial file, classify it as stale, unlink it, and create its own lock (`web/server/billing-export-jobs.ts:473-491`). The first process retains a valid descriptor to the now-unlinked inode and still sets `runnerLockHeld = true`, so both proceed.

```
process A                         process B
open(lock, O_EXCL) succeeds
                                  open(lock, O_EXCL) -> EEXIST
                                  read/parse empty lock -> invalid
                                  unlink(lock); create new lock
write PID to unlinked inode
start runner                      start runner
```

Both runners can execute the same queued job, race work-directory deletion/recreation, and lose `db.json` updates across processes. Retry unreadable locks for a bounded startup grace period and reclaim only once age proves staleness, or use a lock primitive whose ownership cannot be stolen by unlinking metadata. A child-process test should hold the lock between create and write and prove that exactly one runner starts.

## Shutdown and cancellation leave two lifecycle gaps

The browser close handler is registered only after `await puppeteer.launch()` resolves (`web/server/billing-exporter.ts:357-383`). If launch stalls after creating Chrome, `stopBillingExportRunner()` aborts and waits while `index.ts` exits after 30 seconds (`web/server/billing-export-jobs.ts:543-545`, `web/server/index.ts:142-144`); no `Browser` handle exists for `closeBrowserBounded()` during that interval. This is a **confirmed Medium** PM2 cleanup gap. Give launch a timeout below the shutdown deadline and track/terminate a launched child even when Puppeteer never returns a `Browser` object.

Queued cancellation calls `cleanupWorkDir()` before persisting `cancelled` (`web/server/billing-export-jobs.ts:221-226`). A permission, filesystem, or transient deletion error returns 500 while the job remains queued and eligible for execution. This is **confirmed Medium**. Persist cancellation first, then perform best-effort cleanup with retry/reporting.

## Large-download behavior diverges by browser — confirmed Medium

`handleDownloadExport()` awaits a status request before calling `showSaveFilePicker()` through `downloadBillingExport()` (`web/client/src/pages/Billing.tsx:336-347`, `web/client/src/api.ts:245-257`). The picker requires transient user activation; if the status round trip outlives that activation, Chromium throws `SecurityError`, which is rethrown without fallback. Open the destination from the original click before any network await, or let the authenticated download endpoint return 409/410 without a separate preflight.

Without `showSaveFilePicker`, the fallback calls `res.blob()` before triggering an anchor download (`web/client/src/api.ts:294-302`). Safari and Firefox therefore hold the complete ZIP in browser memory. Make the browser support boundary explicit and enforce a safe fallback limit, or provide an authenticated streaming mechanism that does not materialize the response in JavaScript.

## Concurrency invariants have no automated regression coverage — confirmed Medium

No billing export test file or test script exists in the scoped change; only source and generated `dist` matches were found. Add deterministic coverage for owner conflict, queue limits, queued/running cancellation, abort during Chrome launch and zip, shutdown recovery, sweeper-versus-download leases, repeated TTL downloads, and owner/admin authorization, including a real multi-process lock-contention case.

## Audit completion and live announcements are inaccurate at the edges — confirmed Low

The download route writes `BILLING_EXPORT_DOWNLOAD` before `await pipeline(stream, res)` (`web/server/routes/aws.ts:775-785`). A disconnected client or failed transfer is still presented as completed. Record a “download started” action at that point and the outcome after the pipeline settles, or defer the action until success.

The entire progress panel is a polite `role="status"` live region while polling replaces progress and timestamps every three seconds (`web/client/src/pages/Billing.tsx:453`). Screen readers can repeatedly announce incidental updates throughout a long export. Keep the detailed panel outside the live region and expose a concise, throttled message for phase or terminal-state changes.
