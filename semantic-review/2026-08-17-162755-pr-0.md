# 账户清理器第三轮：三项 High 已关闭，coverage 与 protected-KMS 仍阻断放行

当前实现已把 enabled-region coverage、全局 scanner、CloudFormation exactly-one ownership 和父作用域 identity 纳入 fail-closed 路径；`scan`/`plan` 的可达 AWS 操作仍限于 STS 与 list/get/describe 类读取。上一轮 4 个 High 中，protected stack 完成语义、CFN owner 匹配、EKS/EventBridge identity 已关闭；coverage 只在“当前恒有 gap，因此零写”这一层关闭，仍不能安全解除。新增的 KMS guard 因调用前过滤而永远看不到 protected residual。Watch for: **[High][confirmed]** covered 的 DynamoDB/Lambda/EC2 仍有未枚举资源族，清空静态 gaps 后可假 clean；**[High][confirmed]** protected 非 IAM 资源存在时仍可调度 KMS key 删除；**[Medium][confirmed]** `max_rounds` 可先于 async deadline 停止。

**Verdict**: NEEDS_CHANGES

## High-level view

当前版本实际运行仍安全拒绝删除：`KNOWN_COVERAGE_GAPS` 恒非空，runtime botocore 未分类模型也追加 gap；每个 enabled region 必须有完整、唯一、成功的 regional scanner coverage。任何 issue 或 coverage 不完整都在 `delete_round` 前停止，且只读路径未发现资源写 API。

coverage 契约仍只到 service-model 粒度。一个 model 被标为 covered 后，其中未被 scanner 枚举的资源族不会自动形成 gap；解除当前静态 gaps 后仍可能漏资源。

protected stack 与非 IAM 后代现在不会自动删除并持续阻止 verify/nuke complete；明确 access-chain IAM 闭包和精确默认 VPC baseline 才是 allowed residual。KMS defer 却基于过滤后的删除列表，protected residual 已被丢弃。

CloudFormation 非删除态 mapped physical reference 现在要求 exactly one match，零/多匹配均 blocking。EKS 子资源和 EventBridge rule 使用 ARN 或 parent/name 复合 identity，删除仍使用 metadata 中的真实 parent/name。

EKS/DynamoDB lifecycle status 已进入 fingerprint，普通 no-progress 不再抢在活动 async resource 前触发；外层 `max_rounds` 仍可抢先耗尽。

## Coverage 当前保证零写，但无法安全解除

regional/global manifest 与实际 scanner tuple 绑定（`scripts/cleanup.py:69-86, 1048-1050, 1510-1512`）；`expected_coverage_keys` 要求每个 enabled region × regional scanner 及全部 global scanner，并拒绝缺项、重复、failed 和任意 gap（`scripts/cleanup.py:323-338`）。runtime 把 `get_available_services() - COVERED_BOTOCORE_SERVICE_MODELS` 转成 gap（`scripts/cleanup.py:899-907`）。`nuke` 在 `scripts/cleanup.py:2900-2915` 检查 issue/coverage，写入口到 `scripts/cleanup.py:2945` 才出现；静态 gaps 当前恒非空，所以删除器不可达。

**[High][confirmed]** `dynamodb`、`lambda`、`ec2` 已被整体标为 covered（`scripts/cleanup.py:79-86`），但 DynamoDB scanner 只有 table（`scripts/cleanup.py:1358-1366`），Lambda 只有 function（`scripts/cleanup.py:1197-1199`），且没有 DynamoDB backup、Lambda layer version、EC2 Capacity Reservation/Spot request 的 scanner、deleter或 gap。本地 pinned botocore 模型确认对应 API 存在。清空现有静态 gaps 后，这些资源不会阻止 `coverage_complete`，可形成假 clean/complete。

## Protected 完成语义已关闭旧问题，KMS 引入新不对称

`classify_resource` 只允许 access-chain IAM role/profile/customer policy 与精确 default-VPC baseline 残留；其他 `preserve` 对象均为 `protected_residual`（`scripts/cleanup.py:1923-1930`），并继续进入 verify/nuke residual（`scripts/cleanup.py:2831-2836, 2975-2982`）。IAM scanner保留 role 的 attached policy、permissions boundary 和 instance profile（`scripts/cleanup.py:1530-1573`）；未发现访问链被放入删除集合的路径。

**[High][confirmed]** `command_nuke` 在调用 `delete_round` 前只保留 `delete`/`schedule`（`scripts/cleanup.py:2915-2919`），因此 `protected_residual` 不会传入。`protected_service_resources_remain`（`scripts/cleanup.py:2087-2101`）恒为 false；只剩 protected 非 IAM 资源和 customer-managed KMS key 时，key 仍会被安排删除。KMS guard 必须读取完整 inventory 或独立 residual context。

## CFN exactly-one 与父作用域 identity 已关闭旧问题

每个有 physical ID、非 `DELETE_COMPLETE`/`DELETE_SKIPPED`、已映射的 CFN reference 都要求 exactly one inventory match；零匹配产生 `ownership_unknown`，多匹配产生 `ownership_ambiguous`，两者均阻断 nuke（`scripts/cleanup.py:1825-1863, 2900-2915`）。未知 CFN type 同样 blocking。

EKS 子资源以 ARN 为主、`cluster/name` 为回退，EventBridge rule 以 ARN 为主、`bus/name` 为回退（`scripts/cleanup.py:1337-1356, 1392-1401`）。删除 API 从 metadata 取 EKS `cluster`/`name` 和 EventBridge `event_bus`/`name`（`scripts/cleanup.py:2224-2253, 2278-2289`）；同 key 不同 ARN/metadata 产生 blocking `ConflictingResourceIdentity`（`scripts/cleanup.py:909-933`）。

## Lifecycle 修复仍受外层轮数限制

EKS 三类子资源和 DynamoDB table 的 status 已进入 fingerprint（`scripts/cleanup.py:87-100, 1341-1366`），`consecutive_no_progress` 仅在无 current async 时触发（`scripts/cleanup.py:2965-2968`）。

**[Medium][confirmed]** `max_rounds` 可配置为 1，而 deadline 最低 300 秒；`range(1, max_rounds + 1)` 会让活动 async resource 提前退出（`scripts/cleanup.py:2881-2896`）。最终 residual 会阻止假 complete，但 deadline 尚未真正优先。
