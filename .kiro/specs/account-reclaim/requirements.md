# requirements.md — 账户回收

## 目标

交付账户给客户时，我们同时交付 AWS Root 密码、根邮箱及邮箱密码，并可能将该邮箱的邮件转发给客户。
因此，客户离场后，即使只修改 AWS 密码，客户仍可能通过旧邮箱密码或邮件转发拿到“忘记密码”的恢复邮件，
再次设置 AWS 密码并继续使用账户、产生费用。

账户回收将工具箱已有的 Root 操作与邮箱平台已有的删除转发、修改密码能力组合成一次完整操作，
收回上述交付入口的控制权。新增工作集中于统一入口、按顺序调用、进度与失败原因展示、重试及结果保存；
具体的 MFA 删除、恢复条件设置、AWS 自动改密、邮箱改密和转发删除继续复用原有实现。

这里“清除客户访问”具体指：删除客户转发、使客户旧邮箱密码和旧 AWS 密码失效、移除客户 Root MFA。
账户和根邮箱保留，恢复邮件仍由我们控制的根邮箱接收。完成后可查看并复制新 AWS Root 密码与新邮箱密码。

五个动作（按执行顺序）：

1. **删除邮箱转发** —— 切断客户接收后续恢复邮件的转发入口，保留邮箱正常收信。
2. **改邮箱密码并踢旧会话** —— 使客户旧邮箱密码失效，停止已有 IMAP/POP3 会话，先收回根邮箱。
3. **删除 Root MFA** —— 移除客户绑定的 Root MFA，收回该验证入口。
4. **允许恢复密码** —— 复用工具箱已有的恢复条件设置；已开启视为满足。此时根邮箱已由我们控制。
5. **改 AWS Root 密码** —— 复用 `/rootreset` 自动改密执行器，使客户旧 AWS 密码失效，保存我们的新密码。

操作者流程：选择可回收账户 → 核对清单与数量、TOTP 确认 → 后台依次执行五步 → 查看逐步结果及新密码。
只有五步全部满足才显示“回收完成”；失败或结果未知必须保留已执行事实与处理建议，不能把部分操作成功当作完成。

> 用户原始顺序为 MFA → 恢复密码 → AWS 密码 → 邮箱密码 → 删转发。
> 2026-10-14 第一次调整为「先删转发」；同日 P1 再调整为「改邮箱密码提前到第 2 步」——
> 否则第 5 步的 AWS 重置邮件到达时客户仍能用旧邮箱密码或已登录的邮件客户端看到并抢先点开链接。
> 两次调整均经用户确认。

## 使用者与角色

- 新增独立权限字段 `account_reclaim_access`（`none` / `operate`）。admin 恒为 `operate`；
  `partadmin` / `viewer` 默认 `none`，需在「设置 → 用户」显式授予。旧用户不自动继承。
- 非 admin 只能看到、重试、停止本人创建的批次，查看本人批次的密码；admin 全局可见。
- 页面挂在现有 `cleanup`（资源清理）页下，作为新 Tab「账户回收」；原资源清理保留为第二个 Tab。
  有 `cleanup` 页面权限**或** `account_reclaim_access=operate` 任一即可进入该页，Tab 按各自权限显示。

## 范围内

1. 「账户回收」Tab：账户搜索与勾选（最多 20 个/批）、预检结果展示、TOTP 二次确认创建批次。
2. 预检：Root 邮箱必须托管在 EwoMail 邮箱服务器上（域名托管 + 邮箱存在 + 启用）；
   不满足的账户在列表中置灰并说明「邮箱不在邮箱服务器上」等具体原因，不可勾选。
   另有 AWS 硬约束预检：必须是组织内成员账户、不是 payer 自身（`AssumeRoot` 对 payer 一定失败，
   提前拦截避免「转发已删、第二步才失败」的半截状态）。
   受限账户（敏感权限客户）仅 admin 可回收：非 admin 预检置灰并说明原因；admin 可勾选，确认框单独提示。
3. 后台按账户串行执行五步，状态持久化，服务重启可恢复/如实标记中断。
4. 页面逐账户 × 五步展示状态（待执行 / 进行中 / 成功 / 跳过 / 失败 / 结果未知），
   **任何一步失败或未知都必须在页面写明：哪一步、原因、建议怎么处理**；不得只显示「失败」。
5. 第 1–4 步任一失败：该账户停止，后续步骤标明「因第 X 步失败未执行」；可在 TOTP 确认后从失败步骤重试。
6. 第 5 步（AWS 密码）失败或 `password_unknown`：账户整体标为「部分完成」并显示原因（此时邮箱已收回）；
   明确未提交过密码的失败可 TOTP 后重试第 5 步；`password_unknown` 遵守 ROOT_EMAIL.md 语义，
   **绝不自动重试、也不提供重试按钮**，页面建议用已收回的根邮箱手工走 AWS「忘记密码」确认。
6a. 第 5 步执行器进入「手工输入验证码」时，回收页提供手工输入入口（复用现有验证码弹窗）。
6b. 回收产生的 Root 改密任务只在回收页展示与操作，不出现在 `/rootreset`，也不能经 `/rootreset` 接口取消、重试或下载。
7. 邮箱新密码由 AWSTool 用 CSPRNG 生成，先加密落盘再调邮箱接口；结果不明时用同一密码幂等重试。
8. AWS 新密码与邮箱新密码 AES-256-GCM 永久加密保存，页面可反复查看、复制；每次查看写审计。
9. 邮箱侧复用现有删除转发、改密码及踢会话能力，按 `mailbox-api-spec.md` 对接调用；
   邮箱平台由用户维护，AWSTool 只实现调用适配，不重写邮箱业务。现有能力与生产接口可调用状态分别核验。
10. 审计与飞书通知：批次创建、每账户完成/失败/部分完成、查看密码；均不含明文密码或 reset URL。

## 明确不做

- 不重写 EwoMail 侧已有功能；邮箱侧的接口与部署由用户维护，工具箱按 `mailbox-api-spec.md` 调用。
- 不删除或改动「资源清理」现有功能与接口。
- 不处理账户内其他访问面：IAM 用户/角色/Access Key、Identity Center、SSO、账单联系人、备用联系人。
- 不删除 Root Access Key（现有账户页已有单独入口，本期不并入）。
- 不改 EwoMail 的 md5 密码存储方式。
- 不支持 payer 管理账户自身、已离开组织的账户、Root 邮箱不在 EwoMail 的账户。
- 不做 CSV 导出（页面查看/复制即可）。
- 不改现有 `/rootreset` 的页面、权限语义与执行器行为（只加最小接入点）。

## 验收标准

- [ ] `cd web && npm test && npm run typecheck && npm run build` 全绿，含新增
      `tests/account-reclaim*.test.ts`
- [ ] 无 `account_reclaim_access` 的 partadmin：看不到「账户回收」Tab，直调 `/api/aws/account-reclaim/*` 返回 403
- [ ] 只有 `account_reclaim_access=operate`、没有 `cleanup` 页权限的用户：能进 `/cleanup`，只看到「账户回收」Tab
- [ ] 账户列表中 Root 邮箱域名不在 EwoMail 的账户置灰并显示原因；payer 自身置灰并显示原因；受限账户对非 admin 置灰并显示「仅 Admin 可回收」，对 admin 可勾选
- [ ] 测试替身（邮箱接口 + AWS + 执行器均 mock）跑通：全成功 → `completed`；第 3 步失败 → `failed`
      且 4/5 标「未执行」；第 5 步 `password_unknown` → 整体 `partial`、第 5 步不可重试；
      第 2 步首次超时 → 同一密码重试成功
- [ ] 服务重启：执行中的第 1–4 步可安全续跑；第 5 步状态以 root-email 任务为准
- [ ] 回收产生的 Root 改密任务不出现在 `/rootreset`，经 `/root-email/*` 接口取消/重试/下载均被拒绝
- [ ] 邮箱侧接口可调用并通过自检后，EC2 上用一个授权测试账户完整跑通五步，页面能查看/复制两个密码，
      用新 AWS 密码登录 Root、用新邮箱密码登录 webmail 成功，客户原转发地址不再收到邮件
- [ ] 邮箱回收验收同时覆盖已登录的旧 webmail 与 IMAP/POP3 客户端：旧会话不能继续读取新的恢复邮件；
      只验证旧密码不能重新登录不足以证明找回入口已收回。

## 已知约束

- `AssumeRoot` 只对本组织成员账户有效，会话 900 秒，需区域性 STS 端点；payer 的 `role/tool` 需 `sts:AssumeRoot`，
  组织需开启集中式根访问。
- 第 5 步复用的执行器全局浏览器并发为 1，每账户同时只能有一个 root-email 任务、创建间隔 ≥ 60 秒，
  全局最多 500 个待处理任务；批量回收的第 5 步会与 `/rootreset` 的任务共享队列。
- 邮箱 API 出口白名单为 EC2 `54.255.131.45`，Mac 本地无法联调真实邮箱接口。
- 邮箱平台已有相关业务功能；工具箱调用的 API、鉴权与生产连通性仍需按接口规格联调确认。
  接口尚不可调用时使用测试替身开发；生产上「邮箱写接口未配置」时明确提示并拒绝创建批次。
